# 主库所在节点断网：恢复边界与复验

本轮针对上一轮 61 / 360 次失败、其中 10 次限流、5 次工具业务失败和 1 次未确认读取继续排查。旧报告和旧数据不覆盖，不把不同轮次的差额直接当作修复收益。

## 本轮改动

1. 测试控制器增加固定错误分类、网关实例、工具调用开始/返回、回执提交开始/结束，以及未确认读取的请求编号。仅记录生成的测试编号、时间和白名单错误码，不记录工具参数、返回原文、凭据和数据库连接串。
2. 故障健康观测延长到整个负载阶段结束，覆盖节点重新联网后的恢复过程；HTTP 200 的业务失败和客户端传输错误继续计入失败。
3. 受控 MCP 工具服务新增 `/readyz`，复用真实应用的有界数据库可写连接检查；Kubernetes 与入口代理都改用此检查。端口可连接但数据库不可用的实例不能仅凭 TCP 成功就重新分流。此改动属于测试上游及其部署接入，不代表任意第三方 MCP 服务自动获得了数据库就绪检查。
4. 探针失败只停止向该实例发送新请求，不强行切断已开始的工具调用；现有工具、数据库及代理等待上限继续生效。实验性的旧会话强制清退在重复测试中造成正常请求断连和未确认读取，已撤回，详见失败候选记录。重试仍为 0，原并发上限与 60 秒租约不变。

现有部署应为自管上游配置 `gatewayProxy.upstreams[].healthPath: /readyz`，且该端点必须真的检查该实例的业务依赖。保留空路径只代表 TCP 可连接，不能当作完整业务就绪。第三方服务没有这样的端点时，需明确保留这一覆盖缺口，不能随意编造地址。

依据：[HAProxy 健康检查文档](https://www.haproxy.com/documentation/haproxy-configuration-tutorials/reliability/health-checks/)。数据库仍保持严格同步复制；未为了减少故障数字改成可能丢失已确认写入的异步模式。[Patroni 同步复制说明](https://patroni.readthedocs.io/en/latest/replication_modes.html)

## 定向与全量验证

- 实际 HAProxy 3.0 容器对照：同样的两个 HTTP 后端，一个端口开放但业务就绪失败；TCP 检查仍分流到失败实例，HTTP 就绪检查则只使用健康实例。此项是代理子系统验证，不冒称完整 MCP Agent 流程。
- 实际 HAProxy 在途请求验证：健康检查已将网关判为不可用时，不会自动断开已开始的工具请求；受控工具完成后原客户端仍收到成功响应，且工具只执行一次。此项防止重新引入本轮已发现的激进清退副作用。
- 工具就绪检查验证数据库不可用时返回空响应体的 503，不泄漏异常细节；程序错误仍抛出，不伪装成健康。
- 初始候选全量 **728 passed**，启用真实 PostgreSQL 16、Redis 7 与 HAProxy 3.0；报告 `artifacts/verification/network-recovery-20260906-tests.xml`。但完整集群复跑发现下述副作用，说明单元/子系统测试通过不等于高可用验收通过。

## 最后补齐：工具返回后的数据库失败必须说明执行状态

新增 `post_tool_database_unavailable`：只包围工具返回后的处理阶段，数据库可用性异常仍返回失败，不重放工具、事务或模型扫描，也不放出未经完整后置处理的输出。

- 普通 HTTP 路径仍为 503，`detail` 在此特定情形变为结构化对象，包含固定 `code` 与 `tool_execution`；其它普通数据库 503 保持原字符串错误。
- MCP 路径仍为 -32053，在错误 `data` 中保留相同的固定状态。
- 已收到工具响应为 `response_received`，另列工具是否报告错误；传输失败则保持 `outcome_unknown`，绝不冒称执行成功。
- `result_released=false`、`automatic_retry_allowed=false`，没有工具返回原文、SQL、凭据或连接细节，也没有 `Retry-After`。
- 评测控制器分别记录“收到明确执行状态”和“整次业务成功”。原 `executed_without_acknowledgement` 和严格通过门槛保持原义，新字段 `executed_with_failure_confirmation` / `executed_without_any_confirmation` 仅用于区分失败是否仍然含糊，不把失败记为成功。

已用真实 MCP 服务完成 echo 调用，再用真实 PostgreSQL 的事务级只读设置让后续内容写入失败，验证：只调用一次、HTTP 503 明确说明已收到响应、不释放原文、该设置不影响其它事务。另覆盖正常工具响应、工具报告错误、结果未知和 MCP 错误数据传递。此定向测试不等于再跑了一次整个集群断网。

最新候选名为 `agentops-multinode-candidate:20260906-network-outcome1`。上面的四节点指标来自此最后状态反馈改动之前，**最后改动尚未复跑完整集群**；不得把旧指标改挂到新候选上。API/MCP 调用方可以读取新状态，但没有实现跨断网永久结果查询、通用执行去重或新的 Dashboard 状态界面，外部客户端也需要自行消费该错误数据。

## 证据边界

未改扫描规则、模型权重、0.90 阈值、输入上限或旁路模式；本轮不宣称风险识别准确率提高。四个 kind 节点仍共享一台 WSL 物理机，保留入口、Redis 和宿主机单点，数据库使用临时卷，未验证跨物理机、跨可用区及生产峰值。

即使修复后未再次出现未确认读取，也不等于任意断网时客户端一定能收到执行结果。凡结果未知的工具动作仍不能盲目重试。严格故障阶段门槛保持不变：真实失败不会被改记为成功。

本轮三个临时集群已清理，临时数据库内容随集群删除，不能从这些已删除的容器恢复；逐请求记录、回执摘要、失败证据、冻结源码和镜像保留。最后一个集群首次清理遗留了一个已退出的自有 worker，经核对集群标签后定向重试删除成功。宿主 inotify 上限恢复为原来的 128；此前 Windows/WSL 校时设置未改，用户原有的停机容器未动。本轮没有提交或推送 Git 改动。

结论：补齐了上游实例的依赖就绪检查，并定位、修复了“工具已返回却只给普通数据库错误”的信息缺失；否决并撤回了会扩大未确认执行的强制清退。**生产高可用仍未验收通过**：切主期间仍会失败，恢复后还有一次需继续追踪的数据库异常，采样/调度迟滞也限制了部分性能数据的可信度。后续需在保持“不自动重放工具”的前提下，补足可持久查询的执行状态与结果回收，并用独立压测机复验；不能靠修改成功口径或隐藏失败完成验收。

后续复验已完成：上述“最后改动尚未复跑”是本报告当时的状态，最新状态反馈补丁已在完整集群跑出 45 / 360 次失败；之后连接池修复与更快巡检候选两轮均为 46 / 360 次失败。最终 753 项回归通过，但生产高可用仍未通过。详见 [后续优化与全部结果](multinode-recovery-followup-20260906.md)，旧证据与本报告历史数字均保留。
