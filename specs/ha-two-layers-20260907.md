# 两层高可用补充：结果恢复与独立接单

日期：2026-09-07。性质：默认关闭的接单样机和可选结果恢复能力，不是生产 HA 已验收。沿用 [阶段计划](ha-next-steps-plan.md)，不替换既有同步网关、人工审批、任务执行器或 Outbox。未安装 RabbitMQ，未修改宿主机监听额度。

## 第一层：能拿回经过检查的原结果

- 原 v1 回执行为保持：只能确认执行，不伪装成完整成功。
- 新增 operator-reviewed `agentops-receipt-v2`：同一 MCP 服务上的固定结果查询工具及版本，原请求编号、工具名称、结果 SHA-256、大小和保留时间全部绑定。查询参数只有受信执行器生成的 `operation_id`，不能携带任意下载 URL。
- v2 目前仅支持 MCP 文本/JSON 输出，不支持图片、二进制或嵌入资源。摘要为原始结果对象的 UTF-8、键排序、紧凑 JSON 的 SHA-256；不做 Unicode 归一化，不按自然语言摘要认领结果。
- 下游必须把业务效果、摘要和可查询的原始结果可靠保存。合成 MCP 服务把三者放在同一 SQLite 事务中；这证明的是该受控合同，不是任意第三方工具的“恰好一次”。
- 后台 receipt reconciler 先查原回执、再取原结果。查询前后重新检查业务身份、项目权限、工具/合同版本；恢复结果重新走输出策略、原输出结构校验、脱敏和来源标记。已配置的小模型评分失败时不能记录完整扫描成功。
- 只有检查通过才从 `execution_confirmed` 变为 `succeeded`。结果加密保存，有期限；状态接口不返回内容。新 `GET /mcp/invocations/{request_id}/result` 仍使用原业务身份认证，每次读取都按当前权限和策略重新检查，并重新产生来源标记。
- 并发恢复的状态写回受版本条件保护；原执行次数仍为 1。未拿到结果、已撤权、合同变更或扫描失败，均不能重放原动作或自动批准。
- 业务数据库新增迁移 `0019_recovered_tool_results`；原 v1 合同无需升级。旧数据中的空结果字段不授予新能力。

## 第二层：切主期间能可靠接单，但不偷跑任务

流程：受信客户端使用单独接单凭证 → 独立 PostgreSQL 原子保存接单事实和加密请求 → 返回 202 → 导入器按原编号移交业务库 → 原执行器核验权限、策略和审批 → 独立台账更新已观察到的状态。

### 身份和授权边界

- 接单入口不查询业务库，不使用业务库的认证依赖，也不导入/初始化业务数据库。它每次都从自己的库核验接单凭证，没做离线缓存放行。
- 接单凭证由运维命令在业务库健康时签发，绑定现有业务 API key **ID**、项目、Agent、明确工具及已审核版本。只允许提交和查看该身份的请求，**不代表获准执行**。
- 仅保存接单凭证的 SHA-256；原值由运维命令直接写入独占创建的 0600 文件，不打印，不作为命令行参数，不交给 Agent/模型。接单 API 使用 `X-AgentOps-Admission-Key` 认证头，由受信客户端注入；该头不是工具参数。服务默认不打印访问日志，反向代理也必须屏蔽认证头和请求体。
- 接单凭证和业务凭证是两份独立授权，撤销语义不混用。撤销接单凭证立即停止新提交和该凭证的状态访问，但**不撤回已接单工作**；业务权限撤销由导入和实际执行再次检查。业务库失联期间，单独有效的接单凭证仍能提交，但没有获得执行许可。
- 不支持“队列消息里自带批准”。写入等动作仍进入原有审批；测试覆盖“已受理但等待审批，工具执行 0 次”。

### 持久性和恢复边界

- 接单、加密请求、身份与摘要绑定同一事务。只有提交得到成功确认才响应 202；提交结果不明返回 503，客户端保留原编号查询/重复提交同一请求，不换新编号。
- 同项目、同身份、同编号去重，参数不同返回 409。每个身份只建立一份接单 grant，跨入口副本通过数据库行锁序列化去重及额度核验。
- 台账本身就是队列和状态来源，没有另加一个未定义优先级的缓存索引。状态查询证明“已接单”；`businessState` 是最后一次观察值，带 `businessObservedAt`，明确 `businessStatusIsSnapshot=true`，不是实时执行承诺。
- `accepted` 表示接单事务成功，`imported` 表示已经观察到业务库记录，`completed` 表示业务流程到达终态，**仍须看 businessState 区分成功或失败**。审批等待、结果未知、仅确认执行继续跟踪，不冒充完整成功。
- 本轮入口是受限工具的接单/状态小闭环，不是所有 MCP 客户端的无缝替代。普通异步成功仍只在独立台账提供状态；新增 result 接口目前只返回 v2 故障恢复后加密保存的结果，尚不是通用异步结果托管服务。
- 导入器按租约领取工作。业务登记与原任务/Outbox 一起提交后才回写移交状态；若进程在中间退出，下次先查相同编号。旧导入器不能覆盖新租约持有者，业务侧唯一键阻止重复创建任务。
- 接单请求过期后，仍先检查是否已经成功移交，不能把“上次提交成功但没收到确认”误报为未执行。安全移交后删除接单库的加密参数，保留编号、摘要和事实记录。
- 默认每 grant 待处理上限 1,000，保留记录上限 20,000，待导入期限 1 小时。超过额度返回 429，不无限堆积。当前没有自动删除历史去重记录的命令；清理/归档须另行设计去重保留期，不可为腾容量直接删未完成记录。
- 接单库也必须独立于业务库的故障域。签发命令拒绝完全相同 PostgreSQL host/port；别名、共享宿主磁盘等仍须运维核实。仅在同一主库上再建一个 database 不算隔离。
- 接单库自身不可用时，提交和查询都返回 503。当前两容器样机**没有证明接单库自身切主、跨机容灾或备份恢复**。

## 运维入口与回滚

新增模块：`src/agentops_guard/admission/`。无新增 Python 依赖、无默认 Helm 部署，不会启动即对外开放。

受信部署进程注入 `AGENTOPS_ADMISSION_DATABASE_URL`、`AGENTOPS_ADMISSION_ENCRYPTION_KEY`，密钥不进入聊天、模型上下文或命令行。`AGENTOPS_ADMISSION_ENABLED` 默认 false，验收后显式设为 true。生产仅允许 PostgreSQL；SQLite 开关仅供测试。

数据库连接串使用 `postgresql+psycopg` 驱动。独立接单库的复制、备份与密钥轮换需要单独运维；本轮没有替它补出一套 PostgreSQL 高可用部署。

```sh
uv run --offline python -m agentops_guard.admission.cli migrate
uv run --offline python -m agentops_guard.admission.cli grant --key-id KEY_ID --tool-id SERVER_ID:TOOL_NAME --token-file /private/admission-token
uv run --offline python -m agentops_guard.admission.cli serve --host 127.0.0.1 --port 8003
uv run --offline python -m agentops_guard.admission.cli import
```

`grant`/导入命令需要受信业务数据库配置；接单 HTTP 进程不需要业务库密码。凭据轮换和撤销通过 `rotate`/`revoke` 运维命令，不新增公开管理员接口。生产代理需 TLS、连接/请求体/慢请求限制及租户配额；本轮不声称已交付这些部署验收。

回滚顺序：先关闭新提交，保留状态服务及导入/执行器；核清已受理请求并安全移交后才停服务。关闭总开关会同时关闭状态接口，不能在尚有请求时用它代替“只停新提交”的代理路由控制。不得直接删表、删除加密密钥或回滚迁移而丢失待处理请求/结果。

## 数据库尾延迟诊断

集群 `database_probe` 现在同时采集聚合等待类型/事件、最长事务年龄、WAL 写入/同步计数与耗时、提交/回滚计数以及计时开关，保留原连接获取、提交、扫描等分段计时。无 SQL 正文、参数、用户名或凭据。

注意：采样频率不等于精确等待时长；WAL 统计是实例累计值，需同一统计重置窗口做差分；`track_wal_io_timing` 关闭时 0ms 不能解释成零等待。未主动打开计时配置、放松同步复制或修改超时。[PostgreSQL 16 官方统计说明](https://www.postgresql.org/docs/16/monitoring-stats.html)

真实 PostgreSQL 锁竞争测试验证能够采到 Lock 等待且不输出 SQL。**完整 Patroni 同拓扑三轮 600 请求的尾延迟对照还未重跑，因此不能声称已定位或解决原 1.35 秒 p95。**

当前结论：**两层核心功能及受限组件演练通过；原生产 HA 验收仍未通过。** 剩余为完整集群接线和三轮基线、接单库自身复制/切主、尾延迟定位、常驻队列链路与目标环境验收，不能把旧的 46/180、49/180 接单失败直接改写成新网关零失败。
