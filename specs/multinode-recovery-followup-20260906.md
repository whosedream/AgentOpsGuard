4. 若时钟采样仍有送达迟滞，必须区分计时偏差与测量不确定性；不放宽 2% 容差，不删除异常窗口。

官方文档与本机实际 Patroni 4.1.4 镜像源码均确认：`ttl >= 20`、`retry_timeout >= 3`、`loop_wait >= 1`，且 `loop_wait + 2 * retry_timeout <= ttl`。因此不会设置一个实际上被软件强制改回的“10 秒租约”。较短巡检会增加集群协调请求，较短操作等待会更敏感地响应瞬时故障；实验配置不能未经独立环境验证就称为生产默认值。

依据：[Patroni 动态配置](https://patroni.readthedocs.io/en/latest/dynamic_configuration.html)。同步复制提供的安全约束与可用性取舍见[官方复制模式说明](https://patroni.readthedocs.io/en/latest/replication_modes.html)。

### 新候选：闲置旧连接淘汰与可选巡检配置

发现连接已只读时，使用 SQLAlchemy 原生 `InvalidatePoolError` 标记旧连接池代次失效。其它旧的闲置连接在下一次借出之前更新，而不是留给后续请求逐条发现。不会强行关闭借出中的连接，不重放事务或工具。连接仍失败时仍返回失败；网络异常处理及 SQL、工具超时上限未放宽。

真实 PostgreSQL 三连接对照覆盖“两条闲置只读连接 + 一条正在工作的事务”：修改前第二条旧连接仍进入 checkout，测试失败；修改后第二条在借出前替换，正在工作的事务正常提交。证据 `network-idle-pool-before-20260906.xml` 与 `network-pool-targeted-20260906.xml`；定向测试 **63 passed**。

依据：[SQLAlchemy 连接池失效异常](https://docs.sqlalchemy.org/en/20/core/exceptions.html#sqlalchemy.exc.InvalidatePoolError)。这证实了旧连接淘汰行为的改进，并不单独证明它就是此前每一次集群失败的原因。

## 取舍与未完成项

保留已由真实数据库对照证明的闲置旧连接淘汰修复；保留可复现的巡检实验参数，但**不晋级为默认配置，也不宣称能降低失败率**。不同集群节点位置与故障时序会波动，本轮还同时改变了连接池和巡检参数，不能从小幅差额计算因果收益；本轮实际数字没有显示总失败数改善。

上一轮较晚的恢复后错误此次未复现，不等于已证明彻底消除。正常基线与计时检查通过仍不代表多物理机生产高可用：全部 kind 节点共用一台 WSL 宿主，入口、Redis、控制平面和宿主仍有单点，数据库仍为测试临时卷。

目前同步请求在安全切主窗口内直接失败，而不是持久排队。若要进一步减少这部分失败，需要明确改变调用契约：工具执行前持久登记请求，按编号查询状态，切主时有界等待；已派发而结果未知的动作只允许查询、核对，不能自动重做。即使增加查询接口，也不能把“未知”编造成“成功”。等待会增加部分请求延迟，需要单独制定等待上限与异步受理规则，不能一边排队几十秒，一边声称仍满足本轮 1 秒 p95 门槛。
