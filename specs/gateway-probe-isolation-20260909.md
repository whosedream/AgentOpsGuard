## 一、已经实现的针对性修复

原 `/readyz` 将数据库、模型服务、OPA 三个依赖串行检查，并且多次探针共用一个串行工作额度。一次依赖变慢，既增加本轮总耗时，也让同时抵达的代理与 Kubernetes 探针继续排队；Run6 三个网关曾因约 500–563 ms 的探针超时同时退出路由。

现在三个依赖并行检查，每个依赖最多一个工作线程，同时只运行一轮；在同一轮期间到来的探针共享该轮结果。请求取消不会放弃仍在执行的检查、提前释放额度后再堆出一批新检查。已经完成的健康结果不缓存，下一次探针启动新一轮。

- 原数据库可写性检查、模型真实健康和 OPA 检查全部保留；失败仍返回 503。没有把 `/readyz` 改为永远健康。
- 数据库、模型和授权调用没有获得重试或旁路特权；未修改业务并发、评分预算、健康探针 500 ms 门槛、策略或审批。
- 增加的三个线程仅供健康检查，不抢普通工具线程；合并的是同一时刻的健康检查，不是不同用户的认证或工具请求。
- 未预料的程序错误继续暴露，不自动翻译成成功；客户端看到的已知依赖错误不包含私密地址或异常正文。

测试用阻塞事件证明：数据库检查尚未释放时，另两个检查已经开始；12 个并发探针只触发各依赖一次检查。另测首个等待者取消、后续等待者取得真实失败，以及完成后重新检查而不是继续使用旧结果。这证明了具体代码机制，不单独证明宿主 I/O 抖动已经消失。

## 二、补充可复现的宿主观测

每个负载阶段增加一秒一次的 Linux 聚合资源压力、重大缺页、换入/换出、脏页和回写页记录。与原数据库和 etcd 采样共用单调时钟起点，分别保存阶段文件；只有固定数值字段，不读取进程参数、SQL、凭据或业务内容。采样失败保留固定错误类别，不把缺数据记为零压力。

压力累计值需按同一启动期间的时间差计算，不能直接当作阶段压力。CPU 的系统级 `full` 值不能用来证明没有 CPU 竞争；IO/内存的 `some` 和 `full` 含义也不同。数据只反映 WSL 客体，不等于 Windows 物理磁盘定位。[Linux PSI 官方说明](https://www.kernel.org/doc/html/latest/accounting/psi.html)

具体口径：`pressure.*.total_us`、`pgmajfault`、`pswpin`、`pswpout` 为累计计数；`nr_dirty` 与 `nr_writeback` 是当前页数，阶段末减阶段初只是净变化，可以为负，并非阶段累计写入量。原始文件的 `counters_are_cumulative` 不应被理解为所有字段都是累计计数。独立核查使用相邻采样中点的间隔估计压力比例，不将其冒充每次数据库提交的磁盘延迟。

## 三、为什么接单库不是再减一点连接等待就能解决

当前接单入口每次鉴权、登记和查询都依赖同一套接单 PostgreSQL 的当前可写主库。真实配置为 `ttl=20`、`loop_wait=2`、`retry_timeout=3`；应用等待 8 秒，客户端等待 10 秒。

Patroni 官方当前文档仍将主库租约最小值设为 20 秒。网络隔离时要等待旧主租约安全失效，新主才能竞争接管；剩余租约时长和后续接管可能超过应用预算。不能为了短测把旧主保护移除、关闭同步复制或把看见记录冒充可靠确认。[Patroni 动态配置说明](https://patroni.readthedocs.io/en/latest/dynamic_configuration.html)

因此当前实现能明确拒绝、保留原编号、恢复已经可靠接收的任务，但不能保证这种接单库故障期间持续在原时限内接单或查询。资源隔离不使不可达的主库恢复可写；把队列接在原鉴权/登记之后同样无效。

如果接受增加部署组件，下一步应把接单权限、去重编号、加密请求和可查询状态作为一个整体，放到独立的多数副本确认存储中；业务 PostgreSQL、Outbox、审批和执行器保留。候选之一是支持原子条件事务和默认线性一致读的独立 etcd 集群，但不能复用 Kubernetes 的控制平面存储，也不能把“用了三副本”直接称为验收通过。[etcd API 保证](https://etcd.io/docs/v3.6/learning/api_guarantees/)

实施前须明确：同编号与参数冲突规则、权限撤销、容量上限、可靠确认与响应丢失的区别、状态读取来源、保留期、备份、失败回滚及资源预算。验证必须同时包括单节点隔离后可用、失去多数副本时明确拒绝，以及已受理任务不丢失、不重复执行、不绕过授权。目前没有新增或安装这套存储。
