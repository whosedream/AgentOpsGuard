### 第一轮短时故障

- 9 次 HTTP 429 `capacity_exceeded`、6 次入口 HTTP 503，失败响应集中在负载开始后 56.762–59.281 秒。对应 594 条网关入站记录，6 条入口失败没有到达网关。
- 579 次实际读取中 2 条没有成功评分：`mn_bf97282046da:269`、`:274`，最终原因均为 `deadline_exceeded`。共 580 次评分尝试、3 次尝试错误（2 次超时、1 次不可用）；不能将两条已返回 HTTP 200 的旁路漏评分计为扫描完整。
- 三个网关分别在 55.768 / 55.854 / 58.042 秒被代理摘除，在 59.356 / 59.492 / 59.731 秒恢复；健康检查耗时约 500–563 ms。存在三个副本同时不在路由中的窗口，不等于已证明进程崩溃。
- 22 次业务库采样均为可写且提交确认成功，主地址相同；网关事件未记录数据库错误。鉴权阶段 p95 10.424 ms、最大 738.088 ms，不再是旧 10 RPS 中 p95 约 3 秒的鉴权表现，但负载不同，不能据此报告优化倍数或唯一归因。
- 52.877–62.359 秒采样区间，etcd 后端提交均值 45.100 ms、WAL 同步均值 34.700 ms，前一采样区间分别 2.610 / 2.352 ms；该区间 p95 直方图桶上界均为 256 ms，并非精确分位数。同期业务库采到 `WALSync`、`WALWrite` 和同步复制等待。
- 这些支持“共同资源抖动仍是候选原因”，没有证明具体 Windows 进程、宿主磁盘或所有失败的唯一因果。数据库采样不是连续监控，不能宣称完全没有短暂故障。

## 结果查询恢复

三轮独立 v2 结果恢复均通过，观察到完成的时间分别为 4.372 / 26.479 / 30.543 秒；每轮仅一次工具动作、一次效果、一次回执，无客户端动作重试。每轮有 3 条成功评分记录，但其中 2 条缺少请求编号，只有 1 条与恢复编号绑定；保留此观测关联限制，不能声称独立专项的三条评分均逐请求绑定。该模式检查真实结果找回并扫描，旧 `receipt_confirmation_passed=false` 字段不是本次 v2 成功条件。

普通接单入口的强制响应丢失也通过：原编号可靠接单，10 次重复提交都返回可靠确认，最终按同一编号查询取得原结果，重新授权并扫描。完成时间观察上界 50.941 秒；实际工具只执行一次，1 条效果、3 条绑定原请求的成功评分，无重复业务效果。其他恢复场景未发生真实结果找回时，不计作新增的 GET 结果恢复覆盖。

v2 的受控下游账本仍是单副本 SQLite，位于 Pod `emptyDir`；只验证容器/进程重启后的保留，不覆盖 Pod 或节点存储丢失，更不代表第三方工具均支持同等保证。

这说明有界恢复入口能保留明确的响应，本轮没有再出现过去的传输未确认；但可写主库恢复所需时间仍可能超过既有请求时限。查询池虽然有独立配额，仍依赖同一接单主库和实时鉴权，因此库不可达时查询仍会失败。不是继续增大连接池就能解决的问题。

注意：该阶段 `passed=true` 检查的是已受理任务安全恢复，代码明确允许接单库故障时拒绝新请求；真正的持续接单字段为 **`uninterrupted_admission_passed=false`**。报告必须保留这个区别，不得据单一 `passed` 字段宣称生产验收通过。
