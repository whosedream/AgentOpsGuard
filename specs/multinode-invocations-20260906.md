# 持久请求版：完整集群断网、积压恢复与延迟复验

## 测试边界与预先设定的验收条件

沿用四节点 kind / WSL 模拟环境，使用当前原生 WSL 源码构建新镜像。三份网关、三份小模型、真实签名 OPA、Patroni PostgreSQL 主从、Redis、MCP 上游，新增三份真实 RQ worker 和两份 outbox-dispatcher。Key 在受信控制器内生成，仅通过 Kubernetes Secret 投递；报告不保存秘密值、连接串、请求正文或工具原始输出。

- 同步延迟：保持原 1 秒 p95、失败率低于 0.1%、调度延迟 p95 不超过 100 ms 的门槛。延续原混合负载与错误计数，不用恢复后查询覆盖原失败。
- 同步断网：断开当前主库所在测试 worker 的 kind 网络，随后恢复同一节点原地址；记录原始失败、业务回执、断线后状态查询、未知结果、重复执行、未授权写入及扫描完整性。
- 积压恢复：暂停本轮全部队列 worker 后继续提交请求，证明可靠受理不依赖 worker 在线；保存恢复前任务及工具回执快照，再恢复三份 worker，最多等待 300 秒排空。普通读取应成功；预设写动作只能进入审批、不得实际执行。
- 队列断网：投递过程中断开主库节点。202 和最终完成分开统计；数据库不能接单时仍算受理失败。已受理记录不得丢失；未知、未完成、重复执行、越权和扫描缺失均单列，不把 BackgroundJob 完成当作业务完成。
- 测量前、中、后对比 WSL 时钟和 Windows Stopwatch，保留 2% 容差。排队完成时间按状态轮询观测，属于包含轮询间隔的上界，不冒充精确服务耗时。

不调整运行产品的超时、重试规则、数据库复制参数、模型阈值或授权策略。只为固定的两个受控测试工具建立管理员核验队列配置，重试模式为 `never`；不把任意用户工具加入白名单。

这仍是单物理宿主、单 Redis、单入口/控制平面的多节点模拟，不是多物理机、生产存储耐久性或独立压测机证明。`production_sla_verified` 始终不据此置为 true。

### 积压恢复（run3）

`backlog4`：4 RPS × 30 秒，**120 / 120 受理**，HTTP 202 的 p95 104.446 ms。恢复前真实数据库快照：120 条 pending 后台任务、120 条 delivered 投递记录，工具执行回执为 0；证明接单与后台执行分离，不是提前执行完再假装有积压。

恢复三份真实 RQ worker 后，最终 **114 条读取成功、6 条写动作停在审批且 attempts=0**，没有缺失记录、重复执行、未知结果、未授权写入或成功确认缺工具回执。恢复请求发出到全部状态观察完成约 35.395 秒；worker 就绪后观察等待 33.645 秒。提交到预期终态的 p95 观察上界为 54.120 秒，包含 15 秒轮询间隔，不是精确执行耗时。阶段及额外全程时钟校验通过。

**整体未通过：114 次语义评分全部 disabled。** 实际部署查询发现 worker 环境和共享 ConfigMap 都没有语义模型模式/地址；网关本身有 shadow、0.9、远端模型 URL 和 2 秒超时。这是 Helm 后台执行器配置遗漏，不是模型判对或判错，也不是完整评分链路已通过。证据 `run3/worker_semantic_configuration_gap.json`。原规则、工具执行前授权与审批仍运行，但不能宣称异步与同步具有完整相同的小模型评分覆盖。

本轮先完成冻结配置的验证并记录这一失败，不在测量中途偷偷打开模型后混合统计；此配置缺口尚未修复。

### 排队过程中主库节点断网（run3）

`queue_primarynet2`：2 RPS × 90 秒，180 次请求中 **136 次可靠受理、44 次受理失败**（43 次 HTTP 503、1 次传输/解码未得到受理确认；该记录仅保存 HTTP 状态 0，不能进一步断言一定是超时）。不做客户端重投，不把已受理率替代原同步成功率。

节点断网约 30.963 秒。主报告停止观察时：128 条读取成功、6 条写动作等待审批、2 条已受理读取显示 `not_dispatched` 且 attempts=0，另 44 个未获受理确认的编号查询不到记录。两个未完成请求的后台任务仍为 running；136 条 outbox 均已 delivered。未发现受理回执缺失、重复执行、未知下发结果或越权写入，但 **可靠接单不等于最终完成**。128 次评分也全部 disabled，因此扫描完整性不通过。

受理响应 p95 147.294 ms、p99 5434.299 ms；已达预期状态的请求，完成时间 p95 观察上界 88.605 秒。后者排除了两条未完成请求，且后台没运行小模型，不能当作全量请求的完整安全链路延迟。

#### 观察窗口缺口，不能把两个请求视作“已经恢复”

控制器把公开状态 `not_dispatched` 计为终态，实际在接单结束后观察 66.347 秒就退出；这两条请求的后台任务仍处于 660 秒工作租约内。因此本阶段 **没有完整等待原定的最多 300 秒恢复窗口**，更没有证明 11 分钟后的工作租约回收。`accepted_pending_or_unqueryable=0` 不能解释为队列已经排空，`queue_integrity_verified=true` 也只覆盖其有限的重复/越权/已确认缺回执检查，不代表已受理任务全部完成。

源码显示，queued / preparing 可以在后台工作租约回收后重新取得执行资格，公开状态的过期映射本身不代表永久终止。此处是状态含义与测试等待条件需要统一的缺口；本轮不缩短租约、不手工改任务状态、不直接重放工具来填成功数。

恢复工作时已到北京时间 2026-09-07 00:50，WSL uptime 约 63 分钟，临时设置恢复为 128，测试数据库不可访问。只读状态核对失败，见 `run3/post_interruption_observation.json`。已有阶段报告与 54 份相关 JSON 均可解析且已计算哈希，但无法核实这两个请求在中断后的最终结果；不能据此断言丢失或后来成功。中断不改变先前阶段的原始失败统计。

### 队列测试准备错误与修复（run3）

run2 的 backlog4 在 seed 阶段失败，尚未暂停 worker、尚未发送请求。真实 PostgreSQL 上复现 HTTPException 404；原因是 SessionLocal 禁用自动 flush，测试工具刚加入会话还未落表，版本查询看不到它。新增独立 SQLite 回归先复现同样 404，再在测试 runtime 的 queue seed 中补 `db.flush()`，**43 passed**，报告 `multinode-invocation-harness-20260906-seedfix.xml`；Ruff 和 diff 检查通过。

未改业务代码。以新镜像 `agentops-multinode-candidate:20260906-invocations2` 和新集群 run3 执行队列阶段，保留 run2 已完成同步阶段及未完成 backlog4。没有现场替换已冻结测试脚本后偷偷复用原报告。镜像 ID 为 `sha256:9e4e21b5db0a1c21a2bb97c7faf9394eab2da13d72e2eaab6d40bbed363c2a38`；run2 镜像为 `sha256:5e803ef996fc1efd9167ff66d400ed5201206ef194a69f2a0552ed1b43fd31d9`。哈希核对确认，两份 149 文件冻结清单的差异仅为测试 seed runtime 及控制器候选镜像名；业务源码完全相同，当前工作文件与 run3 冻结清单一致，见 `run3/source_comparison.json`。
