# 失联摘除、调用期限与模型排队复测

本轮承接 `multinode-capacity-20260906.md` 的失败项。只修改可靠性路径，不修改规则、模型权重、0.90 阈值、1024 字符模型输入边界及 shadow 模式。

负载组成是 80% 短文本读取、15% 长中文读取、4% 攻击文本读取、1% 未经授权写入探针。实际运行真实 MCP 上游、PostgreSQL、OPA 和小模型，但调用入口为已有 `/mcp/tools/call` HTTP 路由；不是完整 Agent 推理测试，也不是全部 MCP 协议方法的兼容测试。控制脚本虽然加载 120 条公开攻击，当前按请求编号取模的负载序列只会轮转其中 6 个索引，不能把容量测试写成“120 种未知攻击全覆盖”。识别质量仍以单独的固定数据集报告为准。

## 结论

三项可靠性改动已实现，功能回归 **690 项通过**；新增真实 PostgreSQL 并发版本登记修复。**最终候选的完整验收仍未通过，不能宣称生产高可用或真实峰值容量已达标。**

最终候选的 9,000 次长测请求失败 7 次（0.0778%），1 次模型评分不可用、1 次读取未取得客户端成功确认。没有重复执行、未授权写入、成功确认缺回执或返回决策未落库。另有独立主库故障 9 / 360 次失败、主库所在节点断网 96 / 360 次失败。标称 10 RPS 短测也有 2 次评分错误。

本轮又发现 WSL 时钟口径不一致，所有 RPS、秒数和延迟只能保留为本机脚本的单调时钟记录，不能作为独立时钟确认的生产性能。小模型仍为旁路评分，识别准确率没有因本轮排队改动而提升。最终证据索引为 `artifacts/verification/multinode-recovery-20260906-v3/summary.json`。

## 开跑前的标准与范围

- 工具调用真正使用配置期限，连接、初始化和读取响应共用一个期限。期限到达后关闭本地传输并释放本调用持有的并发配额；不提前缩短 Redis 租约、不遗留后台线程替调用“继续执行”。
- 关闭连接不是远端撤销执行的证明。写入调用的响应丢失仍进入 `outcome_unknown`，代理不重试，原执行授权不能重复使用。
- HAProxy 主动检查每个网关、模型和 OPA 副本；网关使用 `/readyz`，模型使用 `/readyz`，OPA 使用 `/health`。500 ms 间隔、500 ms 检查超时、连续两次失败摘除，目标为几秒级；不把单机模拟数字视为生产 RTO。
- 模型按最少在途连接分配，代理每副本最多 1 个在途请求及 2 个等待请求，代理排队最长 200 ms。模型内部仍为 1 个计算 + 最多 8 个等待，等待上限从 250 ms 改为 1 s。存在多个代理时，这个代理限制是每代理的，模型内的锁与队列才是每模型实例的总限制。
- 先复跑 60 秒的 2 / 5 / 10 / 20 / 40 RPS 阶梯，第一档失败即停止升档。5 RPS 目标：请求失败 0、模型漏跑 0、p95 ≤ 1000 ms；不是额外增加机器资源后宣称单机性能提升。
- 独立复跑网络隔离和主库故障，再做 30 分钟 2 RPS 整节点故障浸泡；保留失败报告，核对调用回执、策略记录、模型错误、重复执行、未授权写入及审计链。

执行前调整（第二轮候选完成容量阶梯后、长测开始前确定）：将 30 分钟整节点故障长测提高到 **5 RPS**，验证原先发生排队错误的档位能否持续运行。独立网络和主库故障仍用 2 RPS 对照基线。新长测与旧 2 RPS 长测负载不同，不作同条件故障错误率改善百分比宣传。

## 改动

### 传输和配额

原 HTTP 工具调用会把配置中的 10 秒强制放宽到至少 30 秒；Legacy HTTP 内还重复放宽。改为一个覆盖初始化和调用的明确期限，兼容真正 MCP 客户端使用的 `httpx2` 异常组，只返回固定错误代码，不带远端错误文字。

本地测试集群明确配置工具期限 5 秒，给模型检查、策略落库留出时间；负载客户端仍为原来的 10 秒。产品默认工具期限保持 10 秒，部署者需要让外层客户端/入口期限大于工具期限、排队、后置检查和落库之和。普通的客户端提前断开并不等于自动中止远端工具，不能据此宣称端到端撤销。

### 部署

新增可选 `gatewayProxy` Helm 组件，默认不改变现有部署；固定官方 HAProxy 镜像摘要，不持有应用、数据库或 Vault 凭据。Headless Service 提供副本地址，HAProxy 自行检查，不依赖 Kubernetes 等到 Node 变为 NotReady 才停止转发。

代理同时提供内部模型、OPA 和管理员明确配置的同命名空间 MCP 服务转发。只给网关端口接入公网 Ingress；内部依赖端口不接公网。网络策略补齐精确组件与端口。NetworkPolicy 仍需支持它的 CNI 才真正生效；kind 默认网络不能作为生产网络隔离验证。

模拟中入口代理部署在控制节点，三个业务节点各有网关、模型与 PostgreSQL 实例；代理、Redis、控制节点和 WSL 物理机仍是故障单点，不宣称入口高可用、跨物理机或跨可用区高可用。应用资源和数据库临时卷条件与基线一致。官方镜像索引摘要记录在 setup 报告，kind 导入单平台存档后以本地 tag 使用，并保留实际镜像 ID。

宿主机为 Ryzen 5 5600（6 核 / 12 线程）的 WSL Ubuntu 24.04，约 23 GiB 内存。控制节点容器上限为 2 CPU / 3 GiB，三个工作节点各为 2.5 CPU / 5 GiB，所有节点共享同一宿主机和磁盘。请求的 p95 包含工具、模型和数据库路径，不是 Gateway 自身新增耗时；这里的 5 RPS 也不是已经确认的生产业务峰值。

### 追加修复：首次工具版本登记竞争

20 RPS 的 67 次业务失败包含 66 次限流及 1 次真实 HTTP 500。通过仅提取异常类型/约束名而不输出原始日志，定位到 `mcp_tool_revisions_pkey`：两个副本先查询“版本不存在”，再插入相同版本时发生竞争。

在同一个真实 PostgreSQL 中，用屏障强制 8 个独立事务先读到“不存在”，修复前仅 1 个成功、7 个 `IntegrityError`；最终原子插入修复后 8 个全成功、只有 1 条版本记录，8 个外层事务的独立标记全部保留。报告为第二轮目录的 `revision_race_before.json` 与 `revision_race_after_atomic_insert.json`，最终模块源码摘要为 `958ded576afa792cf4f056e149fb08a0235476ee2ad4b674589a38482b2a98d8`。

采用数据库的 `ON CONFLICT (id) DO NOTHING`，冲突后仅取回同工具、同摘要的版本，不改写不可变记录，不回滚调用方的策略事务。SQLite 与 PostgreSQL 分别使用对应方言，并额外验证 SQLite 外层回滚不会残留记录、其他工具的 ID 冲突不能被误用。设计依据：[PostgreSQL 方言的冲突处理](https://docs.sqlalchemy.org/en/20/dialects/postgresql.html#insert-on-conflict-upsert)、[SQLite 方言的冲突处理](https://docs.sqlalchemy.org/en/20/dialects/sqlite.html#insert-on-conflict-upsert)。测试过的 savepoint 中间方案记录亦保留，但未采用，避免 SQLite 旧事务模式的隐式提交问题。

第二轮测试已结束并清理专属集群；修复后的镜像为 `agentops-multinode-candidate:20260906-recovery2`，后续使用第三轮新目录复跑，不混用两版指标。最终全量回归为 **690 passed in 37.32s**，包含真实 Redis 和真实 HAProxy 配置检查；报告为 `artifacts/verification/deadline-recovery-20260906-revision-tests.xml`。Ruff 与差异空白检查通过。

### 第三轮网络隔离：摘除生效，但数据库切换未过关

`network2`（180 秒、2 RPS）发出 360 次请求，业务失败 **96 次（26.67%）**，p95 10002.437 ms。HTTP 状态为 266 次 200、64 次客户端传输失败、4 次 503、25 次 500、1 次 429；另有 2 次 HTTP 200 未完成业务。269 / 269 次已记录的扫描完成评分，没有模型错误，但这不包含没有走到扫描阶段的请求。

隔离前 `worker3` 承载 `agentops-pg-1` 主库。该节点断网约 30.60 秒后恢复，之后 `agentops-pg-0` 成为主库。代理在故障后 **2.330 秒内** 已观察到失联网关和模型副本变为 DOWN，两个存活网关仍为 UP。这是采样读取完成时间给出的观察上界，不是业务恢复时间。全部 96 次失败发生在故障所在的一分钟；故障前后两分钟各 120 次请求无失败。

从首次 DOWN 到故障后 8.311 秒的后续采样，失联网关和模型的 `lbtot` 分配计数都没有再增长，支持“摘除后不再分配新请求”的结论；不代表已在途请求被成功撤销。

仅提取错误类型的诊断确认存活网关出现 `ReadOnlySqlTransaction`、`AdminShutdown` 和连接关闭错误。主库角色切换及旧连接失效是现有证据支持的剩余问题；日志重复出现的错误标记不能按次数直接换算成独立失败请求。`network2_error_categories_v2.json` 修正了初版对 `cannot execute` 文本的过宽分类，不保存原始日志或凭据。

代码边界也需要明确：当前网关 `/readyz` 检查模型和 OPA，不检查数据库；SQLAlchemy 连接池尚未配置主库角色检查、连接存活预检或数据库操作期限。此次工具传输总期限只约束上游 MCP 调用，不约束调用前后的鉴权、策略和审计数据库事务。因此摘除失联应用副本以后，存活应用仍可能阻塞或在旧的只读连接上失败。不能把这轮修改描述成已解决数据库故障恢复，也不能通过自动重放工具写入来掩盖失败。

对账发现 5 次上游读取没有取得客户端成功确认；重复执行、未授权写入、成功确认缺回执、返回的决策未落库均为 0，审计链有效（3 条审计记录，并非每请求一条审计）。该阶段**未通过**。完整证据位于第三轮的 `network2.json`、`network2_proxy_health.json`、`network2_requests.json` 及节点布置文件。

### 最终候选长测：故障后恢复，但仍有扫描与确认缺口

`soak5_node` 完成全部 **9,000 次请求**。按脚本单调时钟计量，目标为 5 RPS、实际负载持续 1799.824 秒，调度迟到 p95 为 1.759 ms；另行观察到的阶段准备开始至请求文件写出墙钟跨度为 1953.458 秒（包含准备阶段，不是精确业务负载时长）。计时偏差见下节，不以脚本时间冒充真实生产峰值。

### 追加发现：本机时钟口径不能用于生产容量定标

长测期间对照时间戳，发现控制脚本每 60 个单调时钟秒产生的进度文件，在宿主墙钟上间隔约 65.3–65.8 秒。只读的独立 10 秒等待探针得到：`CLOCK_MONOTONIC` 10.000109 秒、墙钟 10.000108 秒、`CLOCK_MONOTONIC_RAW` 10.914524 秒。不同区间还观察到墙钟与单调时钟的增量不一致。当前时钟源为 `hyperv_clocksource_tsc_page`，系统报告 NTP 已同步；这不足以确定异常根因，也不能仅因 NTP 显示同步就认定计时可靠。

原始记录为 `clock_probe_10s.json`、`soak5_node_time_observation.json` 以及各分钟进度文件的时间戳。没有调整时钟、关闭 NTP 或切换宿主时钟源。后续摘要另行保留墙钟观察跨度，不覆盖已经冻结的阶段报告。

**口径修正适用于本轮全文：**脚本的 RPS、运行秒数、延迟和摘除时间均按单调时钟计算。表中的“通过”仅代表原脚本在该计时口径下通过，不是可信外部时钟确认的吞吐或时延达标。上文 +22.22 ms 等差值仅保留为原脚本记录，不能作为已确认的性能改善或代价。请求数、失败数、模型评分状态和数据库回执仍是实际观测，但不能把标称 5 RPS 当作已验证的真实生产峰值。容量定标需要计时正常、独立于被测 WSL 主机的压测端重跑；完整验收继续保持未通过。

## 剩余修复顺序

1. 先处理数据库切主后的旧连接、只读角色和有界数据库操作期限；不可用时明确拒绝或返回暂不可用。不能通过自动重放外部工具写入来提高表面成功率。
2. 对纯文本评分这种无外部副作用的操作，再单独验证有限次数、共享总期限的故障重试，以及模型副本减少时的容量；不要把同样的重试规则套到工具执行上。
3. 使用独立、计时正常的负载端重跑容量和故障测试，再根据实际业务峰值确定发布门槛。本轮没有修改宿主机时间服务，也没有把识别模型从旁路切换为自动授权或拦截。

第一次部署 `multinode-recovery-20260906-v1` 没有开跑容量测试：部署控制脚本遗漏 Helm 的 `--namespace`，Headless Service 的 DNS 指向了 `default`。发现后保留冻结控制脚本及失败记录、清理该专属集群，修复参数传递并增加入口实际就绪检查，以新目录 `multinode-recovery-20260906-v2` 重新部署。没有覆盖第一次失败或把它计为通过。

部署时开启 `gatewayProxy.enabled=true` 后，MCP Ingress 自动指向代理；原有网关 Service 保留。自定义客户端及 Dashboard 的 `env.AGENTOPS_SERVER_GATEWAY_URL` 也应显式配置为 `http://agentops-guard-gateway-proxy:8001`，绕过该入口的调用不具备新增主动摘除能力。模拟负载只走已启用的新入口。
