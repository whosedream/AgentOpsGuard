# PostgreSQL 流复制与受控切主验收 v1

## 目标

确认 AgentOps Guard 的关键数据库状态不只能够从离线备份恢复，也能在真实 PostgreSQL 物理流复制
中同步到备用节点，并在主节点停止后由备用节点继续提供读写服务。本验收直接复用 PostgreSQL 16
自带的 `pg_basebackup`、复制槽、同步复制和 `pg_promote()`，不在项目内实现数据库选主算法。

## 固定场景

`scripts/verify_postgres_streaming_failover.py` 使用摘要固定的本地 PostgreSQL 16 镜像，在独立 Docker
网络和一次性数据卷中完成以下步骤：

1. 启动主节点，应用当前全部 Alembic 迁移，并创建最小复制身份；
2. 使用 `pg_basebackup` 和物理复制槽创建热备用节点；
3. 等待备用节点进入 `streaming`、`sync` 状态，把提交方式切为 `remote_apply`；
4. 通过已有应用状态夹具写入两条审计、一个后台任务和一个已批准执行封套；
5. 在主、备用节点分别复核迁移、状态数量和审计链，并确认主节点 WAL 位置已在备用节点重放；
6. 先停止旧主节点，再调用 `pg_promote()` 提升备用节点；
7. 重新指向新主节点，复核原状态，新增一条审计和一个后台任务，再验证审计链；
8. 删除两个容器、两个数据卷和专用网络。

数据库和复制口令只在受信验证进程中生成，通过权限为 `0600` 的临时环境文件和备用节点口令文件
交付，不进入命令参数、报告或异常文本。最终输出不包含数据库地址、应用正文、口令、审计正文或
工具参数。

## 通过标准

- 备用节点由 `pg_basebackup` 创建，并在故障前达到同步流复制状态；
- 固定测试事务的 WAL 已在停止主节点前重放，主、备用节点的应用状态一致；
- 旧主节点停止且不可访问后，备用节点能够提升为读写主节点；
- 两条原审计、一个后台任务和一个执行封套在切换后仍存在且没有重复；
- 新主节点能够继续写入，切换后的审计链完整；
- 最终确认临时容器、数据卷和网络均已删除。

## 尚未证明

这是单机上的两节点、人工受控切主演练，不是生产高可用结论：

- PostgreSQL 本身不负责发现主节点故障；本测试没有部署 Patroni、云数据库控制面或其他自动选主；
- 旧主节点由验证器先停止，未验证 STONITH、租约或云平台隔离，因此不证明自动防止双主；
- 应用在切换后改用备用节点地址，未验证企业代理、虚拟地址或服务发现的透明重连；
- 当前只证明固定事务零丢失，不代表任意故障时都达到零 RPO；生产 RPO 取决于同步策略和故障模式；
- 未验证数据库 TLS、企业工作负载身份、跨可用区、第三见证节点、网络分区或生产数据规模；
- 镜像按摘要固定，但本测试没有独立验证该生产镜像的签名和来源证明。
