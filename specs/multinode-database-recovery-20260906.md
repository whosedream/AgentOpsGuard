# 数据库切主旧连接与 WSL 计时复验

本轮只补数据库故障恢复和性能计时有效性，不改扫描规则、模型权重、阈值和旁路模式。前轮报告与失败数据不覆盖、不重新解释为通过。

## 实现与验收口径

- PostgreSQL 新连接只接受可写目标；从连接池取出连接时重新检查主库角色与只读状态。旧连接失效后可在业务事务开始前重新建立连接，不自动重放事务和工具动作。
- 新建连接等待默认 2 秒、连接池等待 1 秒、单条 SQL 3 秒、锁等待 1 秒；TCP 未确认数据等待 3 秒并开启 keepalive。可通过设置与 Helm `databaseResilience` 配置。
- 单项等待有上限不等于整个请求、DNS、多个数据库目标、整个事务均有同一个总期限。尤其 TCP 保持确认但服务端整个进程停顿时，不能仅靠 TCP 用户超时保证响应期限；本轮不冒称涵盖所有停机方式。
- 事务中遇到降级只读或服务器关闭，将连接池标记为失效，当前事务直接失败；后续请求重新连接。可用性错误返回固定 HTTP 503 或 MCP -32053，不输出 SQL 参数、连接串或数据库原始错误，不附带暗示安全重试的 `Retry-After`。SQL 语法、唯一约束等程序或业务错误仍暴露，不吞错。
- 网关 `/readyz` 加入数据库可写连接检查；`/healthz` 不依赖数据库，避免数据库故障触发所有网关重启。
- 时钟验收以 Windows `Stopwatch` 对照 Linux wall / monotonic / monotonic_raw，每个采样窗口偏差均须不超过 2%。压测前、运行中、结束后均检查；前置失败不开跑，运行中或后置失败则整阶段不能通过。既不回填修正旧指标，也不把同一物理机交叉校时称为独立压测机。

依据：[SQLAlchemy 连接池故障处理](https://docs.sqlalchemy.org/en/20/core/pooling.html#disconnect-handling-pessimistic)、[PostgreSQL 连接参数](https://www.postgresql.org/docs/16/libpq-connect.html#LIBPQ-PARAMKEYWORDS)、[PostgreSQL SQL 与锁超时](https://www.postgresql.org/docs/16/runtime-config-client.html#GUC-STATEMENT-TIMEOUT)。

## 集群复测

候选镜像 `agentops-multinode-candidate:20260906-db-recovery1`，镜像配置摘要 `sha256:535d6d0828a5d51dcc4bdd7bbe3b2add04bf4b77007cfd3bfbd2ad56d697ae02`。目录 `artifacts/verification/multinode-db-recovery-20260906-v1` 保存冻结源码、配置、计时和逐请求记录。

复用前轮四节点、三网关/三模型/三数据库实例的单 WSL 物理机配置；正常负载与数据库切主分别记录。新增 `primary_network` 故障明确选择当时主库所在节点，避免随机选到副本后误称“主库断网已验证”。数据与回执核对仍沿用原严格门槛，不因为短期故障而放宽通过标准。

### 首次基线失败保留

`baseline5` 发出 600 次请求，6 次 HTTP 503，集中在开跑约第 6–7 秒；588 次上游读取中 586 次评分完成，另有 2 次模型不可用。没有重复执行、未授权写入、成功确认缺回执或决策缺失。入口代理记录 3 次 Layer7 超时及 DOWN；网关没有记录 PostgreSQL 只读、关闭、SQL 超时或连接池耗尽错误。不能把全部错误归因于校时，也不能用复测覆盖这次失败。

时钟验收同时失败：运行中一个窗口的 Windows 参考为 10.01149 秒、Linux raw 为 10.01156 秒，但 monotonic 为 9.50366 秒；后置窗口 wall 又向前跳约 0.522 秒。该阶段所有延迟与吞吐只保留为原始诊断数据，不认定性能有效。

### 校时原因与主机修复

只读 `adjtimex` 探针发现 `tick` 动态变化，读到过 9930、9167，而 `USER_HZ=100` 的正常标称值是 10000。9167 对应约 8.33% 减速，普通的几十 ppm 频率修正不足以解释这一量级。

- 暂停 `systemd-timesyncd` 90 秒：46 次取样的 `tick` 始终为 10000，9 个 Windows 对照窗口全部通过，最大偏差约 0.0343%。未手工设置 tick 或日期。
- 自动恢复服务后再测 90 秒：再次不通过，出现约 5.26% wall 跳变以及约 2.61% monotonic 偏差。原始时钟仍与 Windows 对照一致。
- 这强烈支持 WSL 网络校时与宿主同步相互干扰的判断；没有把其它机器上同类 issue 当成本机根因证明。[微软 WSL 时钟问题记录](https://github.com/microsoft/WSL/issues/12583)、[WSL 校时冲突讨论](https://github.com/microsoft/WSL/discussions/11548)仅作背景；因果判断主要来自本机上述暂停/恢复对照。
- Windows `W32Time` 原为 Manual / Stopped，现已启动并改为 Automatic，沿用原有 `ntp4.aliyun.com,0x9`，未换服务器。实际同步状态为 leap 0、stratum 3，已记录成功同步时间，非仅“服务运行”。
- WSL 的 `systemd-timesyncd` 原为 enabled / active，现改为 disabled / inactive，保留 `hv_utils.timesync_implicit=Y` 与原来的 Hyper-V 时钟源，让本机只有 Windows 这一条校时来源。不重启、不换内核、不硬调 tick，不对已有性能数据作比例修正。

本机恢复原设置的方法：WSL 管理员执行 `systemctl enable --now systemd-timesyncd.service`；管理员 PowerShell 执行 `Set-Service W32Time -StartupType Manual`，如需完全回到原运行状态再执行 `Stop-Service W32Time`。恢复两套并行校时可能再次引入已复现的偏差。本修复仅针对这台 WSL 主机，不作为原生 Linux 生产环境停用 NTP 的建议。

### 调整后的相同代码复测

`calibrated5`：同一冻结镜像和相同 5 RPS / 120 秒负载，600 次请求零失败，594 / 594 次读取评分完成，模型错误 0，全部记录完整性检查通过。p95 为 767.937 ms；前、中、后共 17 个窗口计时通过，最大相对偏差约 0.0624%。这是一次有效计时的单机完整链路短测，不能反推出首次失败全由时钟引起，也不等于生产峰值或长测通过。

真实网关客户端套接字验证 `TCP_USER_TIMEOUT=3000`、`TCP_KEEPIDLE=1`、`TCP_KEEPINTVL=1`、`TCP_KEEPCNT=3`；SQL 参数验证 `statement_timeout=3s`、`lock_timeout=1s`。`SHOW tcp_user_timeout` 显示的是数据库服务端套接字设置，不能拿它代替客户端 `getsockopt` 检查。两份原始记录均保留。

`database2`：2 RPS / 180 秒，360 次请求中 10 次 503，失败请求最慢 193.465 ms；所有请求最慢 1035.356 ms，没有 500 或客户端传输超时。故障后最后一次失败在 4.838 秒，之后第一条成功响应在 5.526 秒，余下 229 次请求全部成功。347 / 347 次读取评分完成，模型错误、重复执行、未授权写入、缺失决策、成功确认缺回执、未确认执行均为 0。全部计时窗口通过。由于切换窗口有真实失败，原有严格阶段验收仍为 **false**，不放宽 0.1% 门槛。

数据库侧观测到：原主库 `agentops-pg-0` 已成为副本，网关 14 条连接全部位于新主库 `agentops-pg-2`，两个副本无网关连接。池观测应读 `database2_pool_connections_v2.json`；初版把 inet 的 text 表示（含掩码）与纯 IP 比较，错误得到空列表，已保留并明确由 v2 取代，不能引用初版证明没有旧连接。

`primarynet2`：明确隔离当前主库 `agentops-pg-2` 所在 `worker2`，实际隔离约 30.783 秒，之后 `agentops-pg-1` 成为主库。360 次请求中失败 61 次：46 次 503、10 次 429，以及 5 次 HTTP 200 但工具业务失败。没有 500 或客户端传输超时，最长请求 5432.076 ms，p95 1040.610 ms。301 次实际发起的评分全部完成（包含失败工具返回的评分，不等于 301 次成功业务），297 次工具读取有回执，其中 1 次未得到客户端成功确认。重复执行、未授权写入、返回决策缺失、已成功确认却缺回执均为 0；审计链检查通过，但只有 6 条审计链记录，不能宣传每个请求都经过独立审计链核验。

网络故障的失败有两段：故障后前约 25 秒为 503；节点重新连网后，故障后约 35–47 秒又出现限流与工具失败。故障后 47.116 秒观察到最后一轮失败之后的成功响应，其后 147 次请求全部成功。不能只报告第一段恢复时间。第二段的具体内部原因尚未证实；固定错误全文对比未匹配到结果，也不能据此断言它不是传输问题。应继续追查节点回归后 MCP 工具链与共享并发名额的状态，而非继续盲目缩短租约或重放结果未知的调用。

该阶段计时检查通过，但失败率、p95 与未确认执行三项均未满足原门槛，因此 **passed=false**。前轮断网 96 / 360 失败与本轮 61 / 360 均保留，前轮计时无效、节点和主库位置亦不同，不能换算成严格同条件的性能提升百分比。

## 结论与边界

数据库旧连接回收、等待上限及可写就绪检查已落地；真实切主后能恢复使用新主库，不自动重放事务。WSL 校时冲突已经通过本机暂停/恢复对照定位并调整，调整后的基线、切主、断网阶段均通过计时校验。

调整后分阶段累计约 600.827 秒、66 个计时窗口全部通过，最大相对偏差约 **0.0932%**。这是穿插诊断的分阶段采样，不是连续长测；未验证电脑重启、睡眠唤醒后的表现。今后的压测仍必须保留计时门槛。

**完整生产高可用尚未通过。** 本轮没有解决网络故障后的全部短期业务失败，也没有把未确认读取伪装成成功；未重跑 30 分钟峰值两倍长测。识别规则、模型质量及旁路模式没有改变。此环境依然是共享同一物理机的四个 kind 节点，入口、Redis、控制节点与宿主机有单点，使用临时数据库卷，不能作为跨机器、跨可用区或生产峰值认证。

最终运行结束时 18 个 Pod 全部就绪、容器重启数为 0。测试集群清理与原宿主 inotify 上限恢复结果记录在本轮证据汇总；镜像、冻结源码、失败记录与报告保留。Windows/WSL 的单一校时来源设置属于本轮有意保留的修复，可按上文恢复。
