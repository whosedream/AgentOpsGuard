# 单机多节点完整扫描链路容量与故障演练

## 范围与门槛

本轮已完成 5 个阶段、4,740 次请求，**未通过高可用与完整扫描容量验收**。
2 次/秒仅通过 60 秒短测，5 次/秒出现 11 次模型排队超时；
30 分钟节点故障长测、独立主库故障、独立网络故障均失败，详情和不可覆盖的 JSON 见下文。
机器可读汇总为 `artifacts/verification/multinode-20260906-v3/summary.json`，
SHA-256 `b5e11911d67938b401441c20e9221669d2fd2d960e580291e3eaaa34ab462050`。
一台 WSL 主机内运行 1 个 kind 管理节点和 3 个业务节点。管理节点限 2 个 CPU、3 GiB 内存，
业务节点各限 2.5 个 CPU、5 GiB 内存。它们仍共享物理 CPU、磁盘、内核及宿主机故障域。
实测宿主为 AMD Ryzen 5 5600，6 物理核 / 12 逻辑核，WSL 可见内存约 23 GiB。

入口使用管理节点映射至回环地址的 NodePort，不用绑定到单个 Pod 的 port-forward 做压测入口。
网关 3 副本、小模型 3 副本、Patroni PostgreSQL 一主两备均强制分散到三个业务节点。
API 与受控 MCP 上游各 2 副本，OPA 2 副本；Redis 与测试控制进程留在管理节点。
复用项目 Helm 模板与既有 Patroni 清单；副本分布、资源额度、网关测试记录入口为明确的测试覆盖配置。

必须同时检查：

- 计划请求实际全部发出，发送延误 p95 不超过 100 ms；
- 请求失败率低于 0.1%，正常文本不能用隔离响应冒充正常完成；
- 每次实际读取上游均有完成的小模型评分，模型错误不能藏在 HTTP 200 中；
- 未授权写入、重复上游执行、返回确认后缺执行收据、已返回决策缺落库均为 0；
- 未收到成功响应但已发生的工具执行单独报告，不自动重试掩盖不确定结果；
- 审计哈希链有效，但该链仅覆盖规则包安装，不冒称每次读取都有完整 Run/Trace/Event。

完整往返延迟包含 OPA、模型、网络及数据库耗时，不与“不含模型/上游的网关自增延迟”混用。
测试扫描收据增加一次同事务数据库写入，其额外开销也包含在结果中。

## 并发评分修复

旧行为是同一模型忙时立即拒绝。现改为每份模型最多 1 个在算、8 个等待，等待上限 250 ms。
队列满、排队超时与推理失败使用固定错误分类传递，并写入旁路错误事件，不保存异常原文。
推理锁、排队名额在成功、超时和异常时均释放。小模型权重、阈值 0.90、输入窗口与评分逻辑不变。

预热成功后，重复就绪探针不再重复跑模型；启动预热失败仍允许后续探针重试。
带真实模型的首次 8 路并发检查为 6 个完成、2 个排队超时，当时同机正在构建镜像，
因此不能据此宣称稳定容量或 8 路并发保证。其意义是验证有限排队确实生效，容量还需后续测量。

新增及已有全量 Python 测试实跑 665 项通过，覆盖率 81.92%。这不是新集群演练通过的证据。
随后补充错误分类与隐私边界用例，语义扫描和多节点脚本的 56 项定向检查通过。
包含补充用例的最终全量检查为 `uv run --offline --no-sync pytest -q`：669 项通过，耗时 68.62 秒；
该次未重新采集覆盖率，不把上一轮覆盖率写成此次结果。Ruff 与 `git diff --check` 通过。
真实模型对已知中英文 320 条样本的顺序复跑没有评分错误，结果与修复前完全一致；
报告为 `artifacts/benchmarks/boundary-quality-v1/managed_scanner_queue_regression_v3.json`，
SHA-256 `8d58a3393d88bf11fb0148a08c2752501b691d11d9d7af6fe7417f4701e56e50`。
因此本轮没有宣称识别准确率提升，也没有消除之前已知的高误报问题。

## 流量与数据

每 100 次请求固定包含 80 次短正常读取、15 次长正常读取、4 次公开攻击文本读取和 1 次未授权写入。
上游是真实 MCP 服务，写工具只记录模拟执行收据，不修改用户文件或访问外部目标。
公开攻击来自已消耗首轮资格的 Boundary Pairs test 固定版本，源文件摘要：
`034523eefaec18c291f9daa7699037acb0e7a91b1aeb1b205878b124f6e18f10`。
这批文本仅用于制造混合扫描负载，不作为新的盲测或本轮识别质量提升证据。

每秒 2、5、10、20、40 次逐级试探，达到失败门槛时记录瓶颈，不把预设最高档写成实测容量。
在最后一个通过的负载档进行 30 分钟长测，再进行节点停止、数据库主库故障和节点网络断开验证。
没有业务峰值输入，因此只能报告此配置的实测承载区间，不能称为生产峰值两倍。

## 隔离与证据边界

- kind 与 kubectl 使用已校验官方摘要的固定版本；所有 kubeconfig 均在测试专属目录中，
  不修改用户默认 Kubernetes 上下文。
- kind 使用空的临时 Docker 客户端配置，避免继承旧代理，不改用户全局代理。
- 测试数据库口令和 API 令牌由受信控制进程生成，经 stdin/Secret 传递，不进入工具参数、模型或报告。
- 只挂载已核对的小模型目录，并且只读；这个模拟命名空间没有宣称通过生产 PSA 与持久卷验收。
- 数据库使用临时 emptyDir，应用测试连接使用测试数据库超级用户；不是生产磁盘、最小数据库权限
  或 TLS 的验收。已有相关独立检查不能自动转为本轮完整负载下的证据。
- 管理节点、入口与 Redis 仍是单点；没有管理面、Redis、物理主机或可用区容灾结论。
- 工具压测经过既有 HTTP tools/call 入口和真实 MCP 上游，不是 MCP 全协议兼容测试。
- API 多副本已经纳入部署，但工具负载走的是现有网关直接访问数据库的策略路径，不代表 API 独立容量。
- 不调用真实业务 Agent 大模型，也不宣称完整 Agent 攻击阻断率。

## 执行和保留

`scripts/verify_multinode_capacity.py` 分为 `setup`、`phase`、`cleanup`。
每阶段开始、故障注入前、每分钟进度和最终结果分别落盘；已启动阶段不可重用同名。
这样中断的尝试仍保留记录，不会被下一轮成功覆盖。中断后的节点与网络需按故障记录恢复或清理。
最终清理仅删除专属 `agentops-mn-*` 集群及其中模拟数据；模型、代码、报告和原有服务不在清理范围。

构建时使用与本机相同的 uv 0.12.1，二进制摘要固定为
`92face6b1f0462ad911857957bd168cd4ae45515e2a2cb3fcc3ecbda3d4d82b1`。
旧基础镜像内 uv 0.9.30 无法读取新缓存格式，首次离线构建失败，未计作运行或验收成功。
测试镜像不复制宿主虚拟环境；仍按项目锁文件离线安装依赖，并在部署前核对镜像内源码摘要。

首次集群 `multinode-20260906-v1` 在导入 Redis 多架构索引时失败：
`ctr: content digest ... not found`，未开始业务负载。改用
`docker image save --platform linux/amd64` 后，原集群中的实际导入已成功；
随后清理该专属集群，以 `multinode-20260906-v2` 重新完整部署。失败尝试的状态文件保留。
该导出方式遵循 [Docker 官方说明](https://docs.docker.com/reference/cli/docker/image/save/)。

第二次部署发现 Helm 模板的真实启动缺陷：`opa run --bundle=/policy/bundle.tar.gz`
将布尔开关误写成带值参数，OPA 1.8.0 拒绝启动。模板改为两个独立参数
`--bundle` 与 `/policy/bundle.tar.gz`，保留签名校验和策略版本约束。
原有静态测试恰好断言了错误字符串，因此同时修正回归用例；34 项 Helm 和编排定向测试通过。
遵循 [OPA CLI 的 run 参数定义](https://www.openpolicyagent.org/docs/cli#run)。
第二次集群未进入业务负载，清理后以 `multinode-20260906-v3` 完整重建；
第三次起同时冻结整个 Helm Chart 的文件摘要，避免部署配置与报告版本不一致。

| 5 | 300 | 0 | 286 / 297 | 671.478 ms | 失败：11 次排队超时 |

## 长测中发现的宿主限制与人工干预

在长测第 600.292 秒停止整个 `worker` 节点，保持 60 秒后启动。
停止前它承载数据库主库；业务失败累计达到 38 后暂未继续增长，新主库接任成功。
但是重启节点的 kube-proxy 反复退出，原主库、API 与网关不能完整恢复；
关键报错为 `failed complete: too many open files`。只读连接检查显示：
该节点内到 API、DNS Service 超时，而直连新主库 Pod 和数据库 Service 可连接。

宿主 `fs.inotify.max_user_instances=128`，`fs.inotify.max_user_watches=524288`；
这与 [kind 官方已知限制](https://kind.sigs.k8s.io/docs/user/known-issues/#pod-errors-due-to-too-many-open-files)
一致。经 WSL 管理入口将实例上限临时改为 512，未写入 sysctl.conf；
kube-proxy 随后恢复，原主库正确以备库身份重新加入。
人工操作和恢复快照分别保存在 `environment-intervention.json`、`environment-recovery.json`。

因此该 30 分钟阶段包含一次宿主环境修复，必须按“故障及恢复诊断”报告，
不能当成无人工干预的自动恢复验收。失败请求仍保留，不因修复后恢复而清零。
后续数据库、网络阶段使用 512 上限，最终清理专属集群后恢复原值 128。

### 30 分钟长测最终结果

`soak2_node.json`：2 次/秒，3,600 次请求，38 次业务失败（1.0556%），判定失败。
请求发送延误 p95 为 1.487 ms，实际完成速率 2.001 次/秒，未用闭环降速隐藏排队。
完整往返 p50 / p95 / p99 为 135.517 / 686.145 / 4070.397 ms。

38 次失败全部落在从 0 开始编号的第 10 分钟窗口：32 次传输错误或超时、
3 次 HTTP 500、1 次 HTTP 429，另 2 次 HTTP 200 返回工具错误。
这说明单看 HTTP 200 或全程平均延迟均不够。不能由分钟桶倒推出精确 RTO。
节点停止动作在第 600.292 秒开始，重新启动返回在第 663.014 秒；
完整副本恢复依赖后续人工调整宿主监听限额，不能写成 63 秒自动恢复。

上游成功读取收据 3,526 条，扫描完成 3,505 次，扫描错误 23 次（21 次不可用、2 次排队超时）。
还存在 2 次上游错误响应的扫描，所以扫描总数不与成功读取数简单一一相等；
应直接使用评分错误分类，而不是用两者相减作为“模型错误数”。
越权写入、重复执行、已确认但缺执行收据、已执行但未收到成功响应、
已返回但未落库决策均为 0。审计链有效，共 3 条记录（安装和上游错误），不是逐请求全量审计。

## 独立故障结果与最终结论

以下阶段均在宿主监听额度临时提高为 512 后执行。每阶段前等待数据库三副本与 API 就绪；
采用同样的 2 次/秒混合负载、真实规则 / OPA / 旁路模型，工具调用不重试。

| 场景 / 180 秒 | 请求数 | 业务失败 | 模型错误 | 已执行但未收到成功响应 | 完整往返 p95 / p99 |
|---|---:|---:|---:|---:|---|
| 第 60 秒删除数据库主库 Pod | 360 | 9（2.50%） | 0 | 0 | 669.559 / 791.261 ms |
| 第 60 秒断开 worker3 网络 30 秒 | 360 | 79（21.94%） | 1 | 1 次读取 | 1033.259 / 10001.007 ms |

两阶段均失败。数据库阶段为 6 次 HTTP 500、1 次传输错误，另 2 次 HTTP 200 工具错误；
网络阶段为 75 次 HTTP 429 和 4 次传输错误。失败均位于第 1 分钟窗口，后续一分钟未新增业务失败。
网络阶段出现一次上游已读取、客户端未收到成功响应的“不确定结果”，因此不能宣称可靠交付或
Exactly-once。三项故障阶段均未发现越权写入、重复上游执行、已确认结果缺收据或返回决策未落库。
这些结论只覆盖受控读取与未批准写入探针，不代表真实副作用工具重试、审批恢复或完整 Agent E2E。

当前结论是：**单机多节点模拟和第一轮容量 / 故障验证已完成，但生产高可用与峰值承载没有达标。**
2 次/秒只通过了 60 秒短测；5 次/秒出现评分排队超时，所以 10 / 20 / 40 档按计划未运行。
含故障的长测和独立故障测试不能用于宣称稳定生产容量，也没有在本轮提升或重新证明识别准确率。

下一轮应优先处理：

1. 根据长文本评分耗时确定排队与服务截止时间，并改善模型请求分配；不通过关闭模型、
   放松扫描覆盖或把错误 HTTP 200 算成功来提高容量数字。
2. 让入口更快停止向失联节点派发请求；将端到端超时、取消和共享并发配额释放衔接起来。
   网络阶段的 75 次限流是重点证据，不宜直接无界放大并发上限。
3. 检验数据库切换后的连接恢复，以及已经发生执行但响应丢失时的状态保存。
   未确认是否执行的副作用操作不得自动重试；本轮没有对真实写入进行这项验收。
