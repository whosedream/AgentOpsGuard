## 1. 鉴权：不再为展示时间排队等行锁

原来每次 API Key 鉴权都 UPDATE 同一条 `api_keys.last_used_at`，这是确定存在的行锁竞争点。该字段用于管理页面展示，未用于撤销、过期、作用域、Agent 绑定或闲置失效判定。

现在每个请求仍读取密钥的真实已提交状态，正常检查撤销和过期；项目、作用域及执行前重新授权仍走原链路。只有展示时间采用 60 秒刷新窗口，且数据库内再次检查刷新条件；可选更新使用 `FOR UPDATE SKIP LOCKED`，正在被锁住时跳过这次展示写入，而非排队等待。

- 只允许展示时间近似，**不缓存认证结果**。无竞争时约一个刷新窗口更新一次，持续竞争/故障时可能更旧，不保证误差永远小于 60 秒。
- 保留原调用者的提交/回滚边界，只更新 `last_used_at`，不覆盖权限或撤销字段；同步 ORM 值不会把对象标脏而触发第二次隐式写。
- 首个真正刷新时间的请求仍需要提交。跳过行锁不能跳过表锁、网络或持久化故障；数据库异常仍暴露，不吞掉失败后放行。
- 撤销提交后开始的新请求仍被拒绝，不宣称此次增加了“终止所有已在途请求”的能力。

PostgreSQL 官方说明：[条件 UPDATE 仍可能等待并重新检查条件](https://www.postgresql.org/docs/16/transaction-iso.html)；[SKIP LOCKED 只跳过行锁，可能得到不完整视图](https://www.postgresql.org/docs/16/sql-select.html)。因此这里只将它用于允许省略的展示更新，原认证 SELECT 不使用该选项。

### 真实 PostgreSQL 对照

最终专项：`artifacts/verification/auth-admission-contention-20260909-run3/report.json` 与 `tests.xml`，PostgreSQL 16.14，**13 passed、0 skipped**。前两次 11 / 12 项探索验证另保留，不相加为独立覆盖数。

三组均使用受控有效、未过期密钥，另一连接持有目标行锁。旧写法组复现原无条件时间戳写入；条件更新组只减少写入；新实现调用真实 `authenticate_api_key`。前两组不是完整替代认证实现，只用于这个已知有效输入的受控对照。

| 写法 | 三次结果 | 控制连接锁阻塞证据 | 鉴权操作耗时 |
| --- | --- | --- | --- |
| 原无条件更新时间 | 3/3 触发锁超时 `55P03` | 3/3 确认等待指定持锁者 | 252–254 ms |
| 仅增加数据库刷新条件 | 3/3 触发锁超时 `55P03` | 3/3 确认等待指定持锁者 | 252–254 ms |
| 新实现，忙时跳过展示写 | 3/3 认证成功 | 持锁者尚未释放，认证已完成 | 3.358 / 3.416 / 3.874 ms |

控制实验故意设置 250 ms 锁超时以有界复现，**没有修改项目运行时超时**。另验证 16 个同时刷新请求全部认证成功且只实际更新一次；最近刚使用的密钥被撤销后，新请求仍拒绝；释放持锁者后，后续请求可正常刷新。

这证明了具体竞争机制和修法，不证明它解释了原 10 RPS 故障的全部原因，也不把局部毫秒数当 HTTP 延迟或生产吞吐提升倍数。

## 2. 接单：给状态查询保留资源，保持恢复入口可达

### 状态查询保留连接

默认 HTTP 工厂将原每进程最多 15 个 PostgreSQL 连接分为 **提交池 12 + 查询池 3**，没有增加总额；相应工作线程等待通道也分开。CLI 和导入器的默认存储构造不改变。

查询池仍连接同一套独立接单数据库的**当前可写主库**，执行原新鲜鉴权与查询，不使用可能延迟的只读副本、业务库或跨请求权限缓存。连接角色检测、失效连接处理和原 8 秒服务端/10 秒客户端预算保留；应用关闭时回收两个自有连接池。

真实 PG 专项占满全部 12 个提交连接并保持不释放：已受理编号仍能经 API 查询，数据库健康探针也可响应；返回 `record_observed` 而非伪造新的持久确认。随后提交撤销记录，下一次状态查询返回 401。该测试使用真实 PG 与进程内 ASGI HTTP 调用，不是经过 Kubernetes 路由的网络故障演练。

### 路由恢复能力与数据库健康分开

以前接单部署将数据库相关 `/readyz` 作为路由探针，共享数据库故障时两个健康的 HTTP 进程也会一起退出路由。代码已证明存在这种机制；没有足够逐连接证据把 Run5 全部 27 次传输未确认都唯一归因于它。

现在受控集群部署使用：

| 端点 | 含义 | 用途 |
| --- | --- | --- |
| `/healthz` | 进程事件循环能够响应 | 存活检查，不依赖数据库 |
| `/recoveryz` | 已启用有界接单/查询恢复处理 | 路由探针，**不保证可提交或请求必成功** |
| `/readyz` | 实际连接当前主库且接单表存在 | 独立数据库健康检查，失败仍返回 503 |

数据库探针使用独立单线程等待额度，不占用默认业务线程队列；提交和查询处理始终做认证。数据库失联时，`/recoveryz` 可响应并不允许返回假 202：新提交、已有编号查询仍会有界返回明确的 503；库恢复后按原编号查询，不重放工具。功能未启用时 `/recoveryz` 和 `/readyz` 都返回 503。

“保留路由”目的是允许恢复处理和明确拒绝，**不是将数据库失败变成健康成功、也不是持续接单通过**。已经验证模拟数据库失联和默认线程队列占满时的应用行为；Kubernetes 接线经过配置回归，真实路由改进幅度仍待完整集群测试。

## 3. 修正下一轮的故障证据

- 旧 `admission_primary_loss_database_timeline.json` 的性能探针实际调用业务库探针，不能用于估算接单库不可写窗口。旧 HTTP 失败、逐编号对账及独立 Patroni 主库探针证据仍成立；原文件不改写。
- 新控制器按故障目标选择业务库或接单库探针，并在报告明确写 `database_target`。接单探针只连接受信配置中的独立接单库；只更新负载开始前创建的测试计数行，不碰业务或凭据记录。
- 接单探针区分 `role_writable` 与 `commit_confirmed`，使用与接单相同的同步提交 WARNING 检查。真实 PG 表锁反例已验证：主库可写但计数写入不能完成时，不标记提交成功；释放锁后恢复成功。
- 请求/状态查询中的连接失败、读超时等保留异常类别；无效 JSON 另记响应错误。只保存固定类别，不保存 URL、认证头、响应正文或异常文本。保留原状态 0 的历史语义：它不是 HTTP 0，也不自动等于超时。
