# AgentOps Guard 生产可用性平台化方案

日期：2026-09-10。状态：建议方案，未批准实施；本轮仅增加此文档。复杂度：高。

## 结论和前提

建议采用“真实独立部署 + 托管高可用基础设施 + Temporal 持久执行 + 保留现有安全控制”的生产路线。重点是减少自行维护的任务调度和恢复逻辑，不是增加另一个长期并行的调度系统。Temporal 作为拟选执行平台，先用一个受控工具完成安全与故障验证；不预先承诺更换组件后一定达标。

这比上一轮“暂不新增存储”的路线范围更大，包含架构迁移、部署和持续费用，必须经用户确认后才能实施。默认假设愿意使用真实多机及托管服务；用户尚未确认云平台、地域、费用上限、数据驻留和网络可达性。本轮未购买、安装、迁移、停用任何服务，未修改既有 SLO 或历史报告。

如果最终仍只能使用同一台 Windows/WSL 主机，可以验证功能和故障恢复逻辑，但本方案不将其认证为真实多机生产可用性。

## 1. 为什么局部修复难以收尾

本项目已经包含同步 MCP 网关、独立接单台账、导入器、BackgroundJob/RQ、Outbox、租约接管、回执恢复、策略与模型等。一个请求跨越多个独立提交点；“数据库提交成功但响应丢失”和“工具执行成功但状态未保存”不是调大连接超时就能消除的情况。

最近一次实测，30 分钟 5 RPS 的 9,000 请求和 8,910 次评分全部通过；同一次运行的短基线仍有 26 次限流、2 次评分失败以及计时异常。说明存在短时跨服务延迟，尚未证明具体宿主负载是唯一原因。不能把已有代码缺陷都归咎于 WSL，也不能靠这个环境证明跨宿主容灾。证据见 [评分长测报告](scoring-queue-soak-20260909.md)。

生产目标应区分服务可用性、安全不变量、任务完成和识别质量，而非要求所有故障下每次调用立即成功。Google SRE 用事先约定的服务目标和错误预算决定可靠性投入，避免无限追逐零故障。[官方实践](https://sre.google/workbook/implementing-slos/)

## 2. 目标架构与责任

| 部分 | 拟采用方式 | 解决的问题 / 保留边界 |
| --- | --- | --- |
| 入口及执行进程 | 独立主机/可用区上的多副本，托管负载均衡 | 单实例退出后仍有其他实例；不能共享唯一宿主与磁盘 |
| 任务生命周期 | 优先 Temporal Cloud；不接受托管时另评估自建 | 保存进度、等待审批、恢复执行、调度评分；不代替业务授权和工具去重 |
| 业务数据库 | 同地域多可用区托管 PostgreSQL | 移交复制、备份、切主运维；切主仍可能短暂不能写 |
| 身份及接单权限 | 独立高可用身份服务和受限接单授权 | 接单/查状态不能再同步依赖业务主库；无法验证身份时拒绝 |
| 安全控制 | 复用 OPA、规则、原始要求对齐、HITL、credential_ref、回执合同 | 此部分是项目核心，迁移不得改变安全决策或让调度器批准工具 |
| 模型评分 | 独立资源池、独立任务队列、有限重试 | 单个评分副本故障不拖垮入口；识别率仍须另做盲测 |
| 审计与结果 | 保留业务审计；结果加密存储、可信执行器读取 | 工作流历史不是生产审计的替代品；结果仍须扫描、鉴权、脱敏 |

Temporal Cloud 官方说明普通 namespace 在三个可用区间复制并在持久化后确认变更；自己的执行进程、鉴权、网络、结果存储也必须有相应冗余。它的服务 SLA 不等于 AgentOps 的端到端 SLA。[官方可用性说明](https://docs.temporal.io/cloud/high-availability)

托管 PostgreSQL 也不是瞬时切主。例如 RDS Multi-AZ DB instance 官方给出的典型切主时间为 60–120 秒，可能更长；该数字不适用于所有数据库产品。[官方切主说明](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZ.Failover.html)

第一版范围为单地域，覆盖选定的单节点/单可用区或业务数据库切主场景；不承诺整个地域、多数副本或所有外部依赖同时故障时持续服务。跨地域异步复制的恢复点不是零，不作为“所有已确认任务绝不丢失”的通用证明。

## 3. 请求如何走完

1. 受信入口核验身份、接单范围和限额；绑定租户、调用者、请求编号、参数摘要及工具版本。接单许可与执行许可严格分开。
2. 将最小必要请求信息可靠保存到执行平台；收到持久确认才返回已受理。超时不伪造成功，客户端只用原编号查询/重试提交；同编号不同内容拒绝。
3. 执行进程读取当前业务权限和策略；需要审批就等待。数据库、授权或凭据服务不可用时停在这里，不执行工具；恢复后重新检查。
4. 受信工具适配器执行，凭据仅在这里解析并注入。对支持去重和结果查询的工具，用同一业务操作编号恢复；不支持的工具出现不确定结果就明确标记未知，禁止盲重试。
5. 对已保存的工具结果独立评分、脱敏并写入业务审计。评分失败只重做评分，不重做原工具；成功、失败、待审批、等待评分、未知结果分别呈现。

标准同步 MCP 客户端继续走原协议，不能把自定义 HTTP 202 接单接口冒充 MCP 工具返回。持久异步路径通过受信客户端/显式任务接口接入，先做兼容验证；迁移前后分别报告同步与异步指标。

## 4. 迁移必须守住的细节

- **唯一执行归属**：请求创建时固定由旧执行器或 Temporal 管理，所有旧领取器识别归属；同一请求不能同时进入两套系统。先迁移新请求，旧任务由原系统排空。
- **业务效果不会自动恰好一次**：Temporal Activity 可能执行多次。支持下游去重的适配器复用稳定操作编号；不支持者关闭自动重试并在断线后查回执。Activity 的默认自动重试不能直接用于付款、发送或删除。[Activity 语义](https://docs.temporal.io/activity-definition)、[重试默认值](https://docs.temporal.io/encyclopedia/retry-policies)
- **调度重放不重用旧批准**：审批通知只携带受信审批记录引用；真正执行前检查当前身份、参数、目标、版本、审批有效性和有效期。撤权不能被工作流恢复绕过。
- **查询不依赖业务执行进程**：最低状态查询从平台已持久化的执行描述/历史读取，区分“已接单、待执行、最后已确认进度”；不能仅用需要 Worker 在线的 Workflow Query。详细状态允许显示带时间的最后确认值，不能伪装实时。[消息查询边界](https://docs.temporal.io/develop/python/workflows/message-passing)、[Python 查询接口](https://python.temporal.io/temporalio.client.WorkflowHandle.html)
- **鉴权必须一起拆开**：本项目当前 `admission/app.py` 的提交和查询均访问接单 PostgreSQL。只替换队列而保留该同步依赖，仍会在接单库切主时失败。使用独立身份服务在线核验接单权限及撤销状态；不以无限期离线缓存来提高数字。身份服务自身故障仍安全拒绝并计入相应可用性统计。
- **请求载荷也要可靠保存**：不能只将编号放进 Temporal，而将必要参数留在故障中的业务库或内存里。限制大小的加密载荷可随工作流可靠保存；大载荷引用独立高可用对象存储，并先确认对象保存再接单。对象存储也有故障、保留期和费用边界。
- **密钥与隐私**：工作流参数、返回值和错误会持久化，业务密钥仍只能存在受信执行组件中。只传不透明引用；敏感业务载荷做客户端加密，索引字段、错误文本、调试 UI 和日志不得含明文秘密。加密密钥轮换须能解读保留期内的旧任务。[载荷加密](https://docs.temporal.io/production-deployment/data-encryption)
- **评分模式明确**：当前旁路模型可改为独立可靠评分步骤，但迟到评分不算同步拦截；若某策略要求评分后才能放行，就必须等待或转审批，不能默认放行。新旧口径并列，不回填旧的漏评分数字。
- **不能只删 Redis/RQ**：Redis 当前还承担并发配额；迁移任务调度不代表可以一并删除限流依赖。Outbox 仍可用于业务事务到审计/通知的可靠投递，只退出重复的任务生命周期管理。
- **可升级与可退出**：工作流存在历史重放约束，需要版本化执行进程、历史重放回归、任务/结果保留和导出策略。不能在灰度途中删除旧处理函数、去重记录、审计记录或解密密钥。

## 5. 分阶段实施和停止条件

下列文件路径是拟改动位置，不表示已经创建或实现；各任务完成后可单独提交。除阶段 0 文档外，均需实施确认。跨阶段按顺序推进；本方案不授权启动代理团队或并行部署。

### 阶段 0：固定验收合同与预算

- **0.1 目标合同**：`specs/production-slo-v1.md` 的后续版本。明确支持的工具、故障模型、正常负载、允许排队时长、评分模式和月目标。保留全部旧指标；新口径不得将旧失败改成成功。验收：每个目标都有分母、截止时间和失败定义。
- **0.2 部署选择**：拟新增 `deploy/production/` 的拓扑与费用清单。确认可用区、身份服务、数据驻留、运行费用上限、监控和值守责任；实测目标地域到 Temporal/数据库的网络。验收：无隐藏单机依赖，预算和网络可达性有证据。
- **0.3 基线冻结**：复用 `scripts/run_two_layer_cluster_verification.py` 与现有审计。固定当前版本、规则和模型到同一独立预生产环境做旧方案对照，不同时升级模型或规则。验收：结果能与迁移后同负载、同硬件、同口径比较。

### 阶段 1：一个可靠接单及查询闭环

- **1.1 执行平台适配**：拟新增 `src/agentops_guard/orchestration/`；只做受控只读工具的启动、持久确认、同编号绑定和状态查询。依赖 0.1–0.3。验收：平台已接单但响应丢失时，再提交不新增业务操作；内容变化拒绝。
- **1.2 独立入口身份**：`src/agentops_guard/admission/app.py` 及新身份适配器。接单与最低状态查询脱离业务主库、旧接单库和业务 Worker。依赖 1.1。验收：业务库停止、全部业务 Worker 停止时，合法请求可受理并查到已受理；无效/撤销凭证拒绝；身份服务不可用不接单。
- **1.3 故障验证**：拟新增 `tests/test_orchestration_intake.py`，复用真实 HTTP 与回执 fixture。检查接单前崩溃、接单后响应丢失、查询越权、平台自身不可用和大小限制。验收：没有虚假的 202、没有编号串租户、没有缺失的已确认请求。

### 阶段 2：迁移安全执行和审批

- **2.1 执行归属与去重**：在 `backend/services/jobs.py`、`tool_invocations.py` 添加迁移归属边界，复用领域登记与回执，不让新旧领取器竞争。依赖阶段 1。验收：并发、切流、旧执行器恢复时每个请求仅有一个负责系统；支持合同的工具无重复效果。
- **2.2 审批及当前授权**：复用网关授权、审批与 `tool_receipts.py`；分别测试等待审批期间重启、批准后撤权、版本改变和过期。验收：未批准/撤权动作实际执行为零，信号或历史回放不能自行批准。
- **2.3 外部动作恢复**：将执行、查询回执、取回结果设为明确步骤，按受信合同设置重试，不使用通用自动重试包住整段调用。验收：工具产生效果后、写回前终止进程，支持合同的工具取回原结果；不支持者保持未知且不重做。

### 阶段 3：评分资源和完整审计

- **3.1 评分任务隔离**：复用 `backend/services/semantic_scanner.py` 与 `semantic_service/`，使用独立资源与队列；同一受控输入、模型版本、规则配置绑定评分身份。依赖阶段 2。验收：停止评分副本或模拟超时，只重试评分，工具效果计数不增加；已要求强制评分的结果不提前放行。
- **3.2 审计和结果读取**：复用 observability、业务审计、credential_ref 和加密结果合同，补齐 Run/Trace/Event/Approval 逐编号核对。验收：业务结果与评分状态分离；受控假密钥在工作流历史、日志、模型输入和结果中零明文命中；导出中断恢复后可核对全部关键事件。
- **3.3 模型质量回归**：冻结未参与调整的数据，分别报告规则、模型、组合的检出和误报，以及评分完成率。验收：调度迁移不改变同输入的决策；不把“模型运行成功”当作“攻击识别成功”。

### 阶段 4：真实环境故障验收和切换

- **4.1 独立压测与故障控制**：在 `scripts/` 复用现有编号审计和 fault fixtures，压测端与服务端不共宿主。旧方案和新方案使用相同负载，逐项停止入口实例、执行实例、评分实例，触发所选托管 PG 的受支持切主；不未经授权破坏云服务。验收见下一节。
- **4.2 灰度与回滚演练**：受控工具新请求先小比例切入，观察后逐步扩大；按租户/工具与稳定请求编号固定路由。验收：切入、切回、执行器升级都不产生双重执行；已接单旧任务保留原状态查询和结果路径。
- **4.3 退出旧路径**：旧队列排空、完成对账、满足保留期后，只停用被取代的导入/租约/任务分发路径；保留仍服务审计通知的 Outbox 和其他 Redis 功能。删除持久数据另行确认。验收：有组件退出清单，而非两套系统无限期叠加。

停止条件：阶段 1 无法做到可靠确认和独立查询，就不迁移高风险工具；阶段 2 出现未授权或重复效果，立即停新请求灰度；阶段 4 对照未改善关键故障指标，就不将 Temporal 升为默认，也不以更宽松阈值判定成功。

## 6. 验收草案：在实施前确认，不追着失败改门槛

| 类别 | 建议验收内容 |
| --- | --- |
| 服务可用性 | 沿用月度 99.9% 目标；同步业务、异步接单、状态查询分别统计。按约定负载内出现的 429/503、超时均保留；计划维护不偷偷剔除 |
| 负载测试 | 以 5 RPS 为工程起点在独立环境连续 2 小时，并做 10 RPS/30 分钟对照，至少 3 轮；这些仍不叫真实业务峰值。实际峰值明确后再测其 2 倍 |
| 延迟 | 保留旧网关自身 p95 <100ms/p99 <250ms 的口径；同步完整扫描仍单独计时。拟新增接单/最低状态查询 p95 ≤1 秒，必须先确认且包含前门鉴权 |
| 故障接管 | 对约定单故障逐轮测：暂定恢复/恢复推进目标 ≤180 秒，依所选基础设施验证后确认；不能把供应商典型切主时间当保证 |
| 已接单请求 | 每轮逐编号核对：零丢失，全部最终进入有据可查状态；成功、拒绝、等待审批、等待依赖、失败、未知分别统计，不能一律算完成 |
| 工具效果 | 支持受信去重/回执合同的工具，重复业务效果为零；不支持合同的工具禁止未知后重做，明确不承诺自动消除所有未知 |
| 积压完成 | 依赖恢复后，对已授权、无需人工等待、下游有可用性保证的约定测试集合，暂定 5 分钟内完成并清空本轮积压；同时披露最慢耗时与最终失败数 |
| 安全与审计 | 未授权高风险效果、明文假密钥泄露、已承诺关键事件的最终审计缺口均为零；真实 Run/Trace 链路必须开启，不能只核对单条摘要 |
| 评分 | 正常容量下全部要求评分的样本在事先约定期限内评分；即时覆盖与补评分分开。模型故障不得误标扫描成功，不以旁路异步化美化旧结果 |
| 超载 | 超出承诺容量时有界排队、安全拒绝、恢复后能消化积压；完整披露 429，不把超载拒绝掩盖为业务成功 |
| 生产观测 | 故障演练和 2 小时测试只是发布证据；灰度连续观测和实际月统计另列，不能凭一次测试宣布月 SLA 已达标 |

99.9% 不是允许未授权动作或丢任务；它是服务响应目标。安全不变量与可用性目标不能互相代偿。人工审批等待不算系统计算耗时，但必须保留总历时；不调整已有历史报告分母。

## 7. 费用、维护和备选

托管减少的是自己维护复制、选主、工作流历史、升级等基础设施的工作，不是消除应用运维。仍需维护工具适配器、审批、身份、加密密钥轮换、模型质量、容量、告警、备份恢复和发布回滚。

截至本次检索，Temporal Cloud Essentials 官网起价为 100 美元/月，按动作、存储、容量及支持等计费；这不是整套系统的报价，业务请求也不等于一个计费动作。还需计算数据库、多机计算、模型冗余、负载均衡、对象存储、身份服务、带宽及监控费用。未确定地域与流量前不报总价、不代为开通。[官方价格](https://temporal.io/pricing)
