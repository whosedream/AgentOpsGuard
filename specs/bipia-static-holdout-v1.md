# BIPIA 外部内容静态保留集 v1

## 总结

这次直接复用 Microsoft BIPIA 官方测试数据，在查看内容和结果前固定数据提交、当时的规则、小模型、
`0.90` 阈值和拼接方式，然后只运行一次。结果说明小模型确实在工作，但当前组合对陌生攻击的
泛化能力仍不合格，必须继续保持旁路观察。

| 集合 | 规则 | 旁路小模型 | 并集 |
| --- | ---: | ---: | ---: |
| 13,750 个攻击组合 | 491（3.57%） | 4,786（34.81%） | 5,264（38.28%） |
| 200 条正常内容 | 1（0.50%） | 12（6.00%） | 13（6.50%） |

攻击并集检出率的 Wilson 95% 区间为 37.47%–39.10%；正常误报率区间为 3.84%–10.80%。
小模型额外找出了规则没有命中的 4,773 个攻击组合，但它远不足以弥补规则缺口，而且带来了
12 条正常内容误报。因此不能让这个小模型决定放行，也不能把并集命中称为实际阻断。

## 分任务结果

| 任务 | 攻击并集 | 正常并集误报 |
| --- | ---: | ---: |
| Email | 1,911/3,750（50.96%） | 1/50（2.00%） |
| Table | 2,804/7,500（37.39%） | 8/100（8.00%） |
| Code | 549/2,500（21.96%） | 4/50（8.00%） |

规则在 Email 和 Table 上命中为零，说明依赖固定说法的检测很难覆盖“换一种任务描述”的攻击；
Code 中规则命中 491 条，但旁路模型只命中 71 条。BIPIA 的文本攻击最长 137 个字符，当前模型
一定能看到尾部攻击，所以 Email/Table 的低检出主要是语义泛化不足，不是简单截断。Code 攻击
中 43/50 个模板超过当前尾部保留长度，截断会进一步放大代码任务的漏检，但不能解释全部问题。

## 数据和运行方式

复用 [Microsoft BIPIA](https://github.com/microsoft/BIPIA) 官方仓库提交
`a004b69ec0dd446e0afd461d98cb5e96e120a5d0`：

- Email 测试上下文 50 条、Table 100 条、Code 50 条；
- 文本攻击 15 个家族、每个 5 种写法，共 75 条；
- 代码攻击 10 个家族、每个 5 种写法，共 50 条；
- 按官方 `insert_end` 方式把攻击放在外部内容末尾；
- Email、Table 和 Code 分别形成 3,750、7,500、2,500 个攻击组合；
- 每个原始上下文只作为一条正常对照，共 200 条。

数据没有复制进项目。`scripts/prepare_bipia_eval.py` 只取得固定提交并建立仓库外裸缓存；加载器逐个
核对官方文件 SHA-256。选择后语料 SHA-256 为
`085d4c01c64b7ebbbd52503cabb5adf008032aca73503ed4720e4e62748132c3`。BIPIA 仓库代码为 MIT；
Email、Table、Code 数据分别源自 OpenAI Evals、WikiTableQuestions 和 Stack Exchange，使用时仍
需遵守各自上游数据条款。

## 已淘汰的替换候选

首轮结果固定后，又把公开、Apache-2.0 的
`protectai/deberta-v3-base-prompt-injection-v2` 固定到提交
`90c9989b1a342275dd0d1a95aad283c04e075671`，在完全相同的文本预处理、规则、`0.90` 阈值和
BIPIA 语料上做了一次替换件比较。它的并集攻击检出为 `3,564/13,750`（25.92%），正常误报为
`40/200`（20.00%），模型 p50/p95 为 `373.03/490.56 ms`；当前 Wolf Defender 对应为 38.28%、
6.50% 和 `255.36/361.17 ms`。

因此 ProtectAI 候选在准确率、误报和 CPU 延迟三项都更差，明确淘汰，不进入生产或模型并集。
报告 `artifacts/benchmarks/bipia_protectai_candidate_regression_v1.json` 的 SHA-256 为
`46dbcba1736ad2feffb7de9da86ce684dcadf59c5abe78d275a74335db91c5a4`。这是数据已经见过后的候选
比较，不是新盲测；保留负结果是为了避免以后重复选择同一不合适模型。

## 已拒绝的长文本分窗方案

首轮结果固定后，又参考 Meta `llama-cookbook` 的 Prompt Guard 推理工具，将“完整文本按
512 token 分段、各段风险取最大值”的思路移植成只用于评测的探针。参考源码固定到提交
`2f22a9eb030f92d0e99227e57e9a1123af1f9532`，文件 SHA-256 为
`29afa64415b07811c22b3c2e27330ee40f9e8edff0a7faf4940b8cfc1c74d424`。本项目实现先对完整文本
脱敏，再按最多 16 段、64 token 重叠进行离线推理；超限会明确失败，不会静默跳过尾部。

这只是复用分窗方法，仍使用当前 Wolf Defender，不是对 Meta Prompt Guard 2 模型的评测。
数据也已经见过，只从 BIPIA 中固定选择 200 个攻击组合并使用全部 200 条正常内容：

| 方案 | 攻击并集命中 | 正常并集误报 | 模型 p50 / p95 |
| --- | ---: | ---: | ---: |
| 当前 512 字符均匀采样 | 126/200（63.00%） | 13/200（6.50%） | 225.73 / 320.84 ms |
| 完整 token 分窗取最大值 | 159/200（79.50%） | 28/200（14.00%） | 304.31 / 2328.22 ms |

分窗找到了更多攻击，但误报翻倍，并且 p95 已超过当前 2 秒远程模型超时。对同一已知切片继续
试探阈值也没有可用区间：阈值 `0.95` 时攻击并集只剩 17/200，`0.99` 及以上只剩规则自身的
9/200；虽然模型正常误报降为 0，但不能以几乎放弃语义召回为代价上线。因此当前模型配合
“各段取最大值”的设计明确淘汰，没有进入生产。后续动态回归只把单次连续、已脱敏副本从 512
字符提高到 1,024 字符，不等同于这里的全文多窗口方案。

## 不能怎样解释

- 这不是 BIPIA 原论文的攻击成功率，因为这里没有让受攻击的大模型回答问题。
- 这不是 Agent 或工具端到端测试，没有发起真实工具调用。
- 13,750 是上下文与攻击模板的组合数，不是 13,750 种彼此独立的攻击写法。
- 200 条正常内容不足以证明生产误报率，尤其每个任务的正常样本只有 50–100 条。
- 当前结果没有通过小模型晋级门槛；真正兜底仍是原始要求与动作对齐、审批和最小权限。
